The benchmark harness surface

This page states the registration and timing surface of the benchmark harness: what each call does, the name it produces, and the precondition it carries. Each section closes with the test that covers it. Every suite named here runs on the counters fake provider, so no test needs a PMU.

Argument families

The five registration macros SG_BENCHMARK, SG_BENCHMARK_CAPTURE, SG_BENCHMARK_TEMPLATE, SG_BENCHMARK_REGISTER_F and SG_BENCHMARK_TEMPLATE_INSTANTIATE_F each declare one handle initialized by the registration, so the family calls chain at the site and the site ends with ;: SG_BENCHMARK(fn).range(8, 1024);. A site with no chain reads SG_BENCHMARK(fn);.

The ten family calls stand on BenchmarkHandle and each returns the handle for chaining: arg, the two args overloads over an std::initializer_list and an std::vector, range, rangeMultiplier, ranges, denseRange, argsProduct, apply, argName, and argNames. Every family argument is a std::int64_t. argName sets the label list to the one label and argNames sets it to its whole list; a later label call replaces the list that stood before. One args call appends one argument list, so args({8, 64}) states one instance of arity two while arg(8).arg(64) states two instances of arity one. range and ranges grow by powers of the range multiplier with both bounds included, the default multiplier is kDefaultRangeMultiplier (8), and rangeMultiplier settles the multiplier for the later range calls of that family. denseRange steps from the low bound to the high bound inclusive. argsProduct takes the product of its lists with the odometer advancing the first list fastest. The free builders sg::createRange and sg::createDenseRange return the std::vector<std::int64_t> lists a family call accepts. A multiplier below 2, a low bound above a high bound, a denseRange step below 1, and an arity or label count unequal to the family arity are SG_REQUIRE precondition violations. A family above kMaxFamilySize (100 instances) draws one warning on the standard error stream, keeps its instances, and the run continues. Expansion completes at the start of speedgunMain, before the filter and the first run. The example family bmArgs in example/benchmark_example.cpp carries the argName labels width and depth.

Each registration site yields one instance per argument, and the instance set is exactly the arguments that call named, whether they come from a list, a range, a step, a product, an apply, a builder or a chained site. An argument list over the bound warns once naming the bound and keeps the instances that fit. A multiplier, range, step, argument name, apply function or builder that breaks a precondition ends the run with that precondition in the message.

Instance names

An instance name starts with the family name and adds one /-joined segment per argument. A segment reads label:value where argName or argNames set a label for that position, and an empty label leaves the segment without one. A family with no family call keeps the family name alone, with no /. The --filter option and list mode match instance names, so one full instance name selects one instance and the --catalog path prints none of them. Two instances with one name are a recoverable error found at expansion: one line on the standard error stream names both instance names, the earlier instance stays, the later instance does not run, and the exit status stays as the runner fixes it.

An instance name is what a filter matches, and one full name selects exactly one instance. A repeated instance name is reported, the first registration is kept, the later one dropped, and the exit status is unchanged. The catalog walk covers the same set without printing rows.

Argument access

State::range(std::size_t index) returns the argument of the running instance at that position and State::rangeCount() returns the argument count. An index at or above rangeCount() is an SG_REQUIRE precondition violation. A family with no family call has one instance with zero arguments, so rangeCount() reports 0 and range(0) violates. A read allocates nothing: the instance owns the storage and the state holds a std::span<const std::int64_t> fixed at expansion. The timed loop keeps its shape, and the loop-shape gate test/loop_shape.sh stays green.

range(i) reads the argument of the instance that runs and rangeCount() the number of arguments it was given. Reading an argument allocates nothing. An index below the first argument or past the last one breaks the precondition of the accessor and ends the run.

Captured arguments

SG_BENCHMARK_CAPTURE(fn, captureName, ...) registers fn once with the captured values bound into the callable, under the instance name fn/captureName. The capture name is one name segment, and the instance takes part in the filter, list mode, and duplicate handling of the instance names above like any other instance. The registration yields the handle, so a site chains family calls: SG_BENCHMARK_CAPTURE(fn, pair, 2).arg(4); registers fn/pair/4.

A capture name groups the values one run records while the instance keeps its own name beside it. The same function may be registered under two capture names, and a chained site carries its capture name into the instance name and its argument into the state. A capture name that collides with a family instance name is settled at the duplicate tier, where the earlier registration stays.

Template registrations

SG_BENCHMARK_TEMPLATE(fn, ...) registers a function template instantiated over one or more type arguments, under the instance name fn< followed by the type list stringified exactly as written at the macro site, followed by >. There is no demangling: the spacing at the macro site is the spacing in the name. The registration yields the handle, so a site chains family calls: SG_BENCHMARK_TEMPLATE(fn, int).arg(8); registers fn<int>/8. The example SG_BENCHMARK_TEMPLATE(bmFill, std::uint64_t) in example/benchmark_example.cpp is an instance named bmFill<std::uint64_t>.

Type arguments appear in the instance name in the order the macro site wrote them, keeping the spacing of that site through a comma and through a nested template. A chained site names each instantiation, and the instantiation the run reaches is the one the type list names.

Fixtures

sg::Fixture is the fixture base class: a virtual destructor and the virtual setUp(State&) and tearDown(State&) with empty defaults. The seven macros below attach a method of a derived class: SG_BENCHMARK_F, SG_BENCHMARK_DEFINE_F paired with SG_BENCHMARK_REGISTER_F, SG_BENCHMARK_TEMPLATE_F, SG_BENCHMARK_TEMPLATE_DEFINE_F, SG_BENCHMARK_TEMPLATE_METHOD_F paired with SG_BENCHMARK_TEMPLATE_INSTANTIATE_F. A fixture instance is named FixtureClass/Method, and a template fixture instance is named BaseClass<types>/Method. The pair runs in the untimed region of every run, the warm-up, calibration, and measured runs included, and the runner builds one fixture object per run and destroys it after tearDown. The state the pair receives is the callback state of the setup and teardown callbacks section: range(index), rangeCount() and iterations() are legal in it, while begin(), skipWithError and skipWithMessage are SG_REQUIRE precondition violations. SG_BENCHMARK_REGISTER_F and SG_BENCHMARK_TEMPLATE_INSTANTIATE_F yield the handle, so a fixture family chains its family calls at the site: SG_BENCHMARK_REGISTER_F(F, m).denseRange(1, 3); expands the fixture record like any family record, one instance per argument list. TableFixture/bmTableTouch, registered with SG_BENCHMARK_F, stands in example/benchmark_example.cpp.

A fixture instance name is the fixture and the method. One fixture object is built and destroyed for each run, and the setup and teardown pair runs once per run, including a run of a fixed-count, repeated or warm-up instance. Untimed work in a setup callback does not reach the reported time, which is the delta of the timed leaf alone. A method reads the argument and iteration counts from the state of its own run, and begin() or skipWithError() called inside the pair aborts the run. A template fixture yields one instance per instantiation, a split pair spans the two halves, a chained site expands into one instance per argument each with its own pair, and a DISABLED_ method is excluded like any other disabled name.

Setup and teardown callbacks

BenchmarkHandle::setup and BenchmarkHandle::teardown attach one callback per slot, and the last attachment wins the slot. The pair runs once around each run, the warm-up, calibration, and measured runs included, in the untimed region, and the order in one run is the setup callback, the fixture setUp, the callable, the fixture tearDown, the teardown callback. The state a callback receives carries the instance arguments and the iteration count: range(index), rangeCount() and iterations() are legal there, while begin(), skipWithError and skipWithMessage are SG_REQUIRE precondition violations. end() stays legal because it is static and touches no state. The harness runs one thread today; the once-per-thread-group rule belongs to a future threads specification.

The setup and teardown callbacks run once per run for a plain instance, a repeated instance and a fixture. A callback reads the arguments and the counts of the running instance from its state. An attachment whose body never runs stays at zero. The wrapping order is fixed: the fixture pair sits outside the callbacks of the instance it wraps. A callback that calls begin(), skipWithError() or skipWithMessage() on a state it does not own aborts the process.

The

The gate is a prefix test on the expanded instance name, held at selection time in source/harness/cli.cpp. An instance whose name starts with DISABLED_ registers, expands, never runs, stays out of the filter match, and stays out of list mode. A fixture method named DISABLED_x runs, because that instance name starts with the fixture class. A DISABLED_ family as the only match of a filter leaves the executable reporting no match, running nothing, and exiting zero.

A family name with the DISABLED_ prefix never runs and never appears in the listed set. The prefix is read only where a name begins, so a fixture method and a name that merely contains it are unaffected. A filter that matches nothing reports the no match and exits with a zero status.

Suite and case naming

BenchmarkResult carries suite and caseName beside name. The suite is the family name up to its first /, and a fixture instance takes its fixture class as the suite. The case is the instance name with the leading suite and its / removed, and an instance name equal to its suite keeps that name as its case. The pair is unique per instance. After expansion the instance list groups stably by suite in first-appearance order, and rows within one suite keep registration order. The console row keeps one name column carrying the full instance name, with the split readable on the result value. A later JSON report reuses the two fields.

The suite and case fields of a result come from the family name and the instance name of the run, and instances of one suite are reported together. Instance names stay unique across the list, and the console prints a single name column.

Two time columns

Every measured row prints two time columns, real time/iter (ns)= and cpu time/iter (ns)=. Each value is a fold over the raw point pair of that run, and the counters library supplies the fold. A pause whose pair the recorder has no room for closes through a running fold over the same leaf, and the column reads the same value in both paths. The CPU column follows machine/thread_cpu until measureProcessCpuTime moves it. The row keeps its other fields around the pair:

<name>  iterations=<N>  real time/iter (ns)=<v>  cpu time/iter (ns)=<v>
        overhead floor (ns)=<v>  endpoint samples=<S>

ResultRow carries the pair as timePerIterationNs and cpuTimePerIterationNs, each one nanosecond per iteration, and carries endpointSamples as the count the row prints. A run that pauses nothing takes one sample pair, so that count reads 2 samples and the timed loop keeps its shape: the loop-shape gate test/loop_shape.sh stays green.

One primary time per benchmark drives warm-up qualification, calibration growth, and the aggregate time statistics, and the CPU selection is that primary time by default. The aggregate line names it: primary time/iter (ns) mean=. A repetition whose primary fold carried a gap disclosure stays out of those statistics, and ResultRow::timeAvailability carries the disclosure.

Each time column is the folded delta of its own leaf divided by the iteration count, so a scripted delta reports exactly the time it names. A core metric keeps its own fold beside the two time columns. The aggregate line is built from the selection the run asked for. A column that run did not print has no place in it.

The process CPU leaf

BenchmarkHandle::measureProcessCpuTime() moves the CPU column of one family to the machine/process_cpu leaf and returns the handle, so the call chains at the registration site: SG_BENCHMARK(bmProcessCpu).measureProcessCpuTime();. The selection stands for every instance of that family, and it combines with useRealTime and with useManualTime, so one row can carry process CPU time beside real time. The call carries the guard the other setters carry: a handle that names no registered entry, or a family whose run started, is an SG_REQUIRE precondition violation. A provider that publishes no machine/process_cpu leaves that benchmark failed with the resolution line the runner already prints for a missing leaf. In example/benchmark_example.cpp, bmProcessCpu carries the call.

The CPU column reads the process CPU leaf and the real-time column the monotonic leaf; both may be asked for at once. Where the process CPU leaf cannot be resolved, the benchmark is reported as failed with a line naming the resolution that was sought.

Real time as the primary time

BenchmarkHandle::useRealTime() makes real time the primary time of one family and returns the handle. From that call on, the qualification test, the growth rule, and the aggregate time statistics read the real column, and the CPU column keeps the CPU fold it carries. The selection excludes useManualTime: the second of the two calls is the SG_REQUIRE precondition violation, in either order. bmRealTime in example/benchmark_example.cpp carries the call.

The time a run treats as primary decides where its growth rule stops, so one scripted sequence reaches a different iteration count under each selection. The aggregate line is read against the column that selection prints, which keeps the primary time the time the report shows.

Manual time

BenchmarkHandle::useManualTime() selects manual time for one family, and State::setIterationTime(std::int64_t nanoseconds) hands the state one iteration time per iteration. The primary time of a run becomes the sum of the accepted values: the harness records it by summation alone and reads no clock for it, so the time-source gate stays clean. The real column shows that sum divided by the iteration count, and the CPU column keeps its own fold. The fivefold real-time stop leaves a manual run alone, so such a run stops at its target or at the iteration cap. A manual benchmark that accepts nothing reports 0.000 ns in the real column and qualifies at the cap. setIterationTime in a callback state is a precondition violation, because that state owns no run to accumulate for. bmManual in example/benchmark_example.cpp pairs the selection with one setIterationTime call per iteration.

A manual time is accepted against the growth rule of the run, and a sum that reaches the cap with nothing accepted in it is reported. The reading is the same whether the manual report arrives before or after the timed loop, so the order of the two carries no meaning.

Pause and resume

State::pauseTiming() stops the timed window from that point and State::resumeTiming() restarts it, and each call takes one sample of every leaf of the run plan. The reported time of a run is the window fold minus the fold of each closed interval:

reported = fold(base, base + samples - 1)
           - the fold of each closed interval

The subtraction reaches every time column and every attached metric fold, so a paused stretch leaves the metric columns too. ScopedPauseTiming(State&) is the scoped form: the constructor pauses, the destructor resumes, and the destructor skips the resume when the run was skipped.

The calls stand inside the timed loop, where the run's sampling window is open, and the loop keeps its shape. The preconditions bound one open pause per run. pauseTiming needs a run state whose sampling window stands open and no pause already open, and resumeTiming needs one open pause. A run carries no fixed allowance of closed intervals: a loop may close a pair in every iteration. A pause still open at loop exit is an SG_ASSERT breach in closeWindow, and the skip and exception path closes an open pair in topUpWindow before the exit sample, so every fold reads a complete pair. A pause in a callback state is a precondition violation, the callback-state rule extended to the pause calls.

Each call costs one sampling action, and the row discloses the cost: endpoint samples=<S> prints the count that run took, so a run with one paused interval prints endpoint samples=4. The room for those points follows the loop, and no fixed allowance bounds it. Before an attempt starts, the recorder reserves the two points of the window plus, from a family's second attempt, two points for each closed pair its previous attempt observed per iteration, capped at 32768 raw points per leaf column. An attempt over the cap reserves no pause room: each of its pairs closes through a running fold at the commit, the columns of the row read the same values as the recorded points produce, and the row ends with pause=folded so the fold is disclosed. A first attempt of a family has no history to size the room by, so its pairs fold and its row carries the token too. bmPaused in example/benchmark_example.cpp holds a ScopedPauseTiming region inside the loop, and a dry run of build/example/benchmark_example prints endpoint samples=4 for it.

A pause removes the time it names: every time column and every attached metric of the run is the window fold minus the pause fold, to the nanosecond. The guard reads the same interval as the explicit calls around it. A loop that pauses in every iteration still completes. A run that pauses nothing reserves no pause room, and a pause that is opened twice, closed twice or closed without an opening breaks the precondition at that call.

Time units

TimeUnit names the scale and the label of a printed time value: NANOSECONDS, MICROSECONDS, MILLISECONDS, and SECONDS. BenchmarkHandle::unit(TimeUnit timeUnit) sets the unit of one family and returns the handle: SG_BENCHMARK(bmMillis).unit(sg::TimeUnit::MILLISECONDS);. sg::setDefaultTimeUnit(TimeUnit) sets the process default that a benchmark calling no unit resolves to when its run starts, and sg::getDefaultTimeUnit() reads it back. The default starts at TimeUnit::NANOSECONDS.

A stored value stays nanoseconds, so the C++ value keeps one unit, and the report applies the divisor at print time: ns 1 ns, us 1000 ns, ms 1000000 ns, s 1000000000 ns. The scaling reaches both time columns, the overhead floor, and the aggregate line, so one line carries one scale, and the metric columns keep their form. The unit resolves when a run starts: the unit call of the family wins, then the default the entry point snapshots at its own start, then the process default at the moment the run starts. A setDefaultTimeUnit call in main before the entry point therefore reaches a benchmark the macros registered during static initialization, and a unit call overrides all three. bmMillis in example/benchmark_example.cpp sets the millisecond unit, and a dry run of build/example/benchmark_example prints its row under the ms label. A command-line unit option belongs to a future command-line specification.

One unit choice scales every field of a line the same way: both time columns, the overhead floor and the aggregate line. A run that never calls the setter keeps the default unit, and the scaling holds for a runner driven without the entry point, and through it.

auto bmCopyCells(sg::State& state) -> void
{
  const auto cells = static_cast<std::size_t>(state.range(0));
  std::vector<std::uint64_t> sink(cells, 0);
  for (auto _ : state) {
    for (std::size_t cell = 0; cell < cells; ++cell) {
      sink[cell] = cell + 1;
    }
    state.setCounter("cells", {static_cast<double>(cells)});
    sg::doNotOptimize(sink);
  }
  // The byte setter takes the total work of the whole run (FR-009).
  const auto bytes = static_cast<std::int64_t>(state.iterations())
      * static_cast<std::int64_t>(cells) * 16;
  state.setBytesProcessed(bytes);
}

SG_BENCHMARK(bmCopyCells).argsProduct({{64, 1024}}).repetitions(3);
auto bmEncode(sg::State& state) -> void
{
  const auto items = static_cast<std::size_t>(state.range(0));
  std::vector<std::uint8_t> buffer(items);
  for (auto _ : state) {
    for (std::size_t item = 0; item < items; ++item) {
      buffer[item] = static_cast<std::uint8_t>(item * 7);
    }
    sg::doNotOptimize(buffer);
  }
  const auto total = static_cast<std::int64_t>(state.iterations())
      * static_cast<std::int64_t>(items);
  state.setItemsProcessed(total);
  state.setBytesProcessed(total);
}

Reading a report row

A run prints a version line, then one row per instance and repetition, and a final AGGREGATE row when the benchmark asks for repetitions.

auto spreadOf(const std::vector<double>& times, double& spread) -> bool
{
  if (times.empty()) {
    return false;
  }
  double lo = times.front();
  double hi = lo;
  for (const double time : times) {
    lo = std::min(lo, time);
    hi = std::max(hi, time);
  }
  spread = lo > 0.0 ? (hi - lo) / lo * 100.0 : 0.0;
  return true;
}

auto bmRows(sg::State& state) -> void
{
  const auto cells = state.range(0);
  for (auto _ : state) {
    for (auto cell = std::int64_t {0}; cell < cells; ++cell) {
      sg::doNotOptimize(cell);
    }
  }
  state.setBytesProcessed(cells * 8);
  state.setLabel("filled");
}

The command line of an example

One entry point reads the command line, and any example binary takes the same options. --list prints the registered instances, --filter selects them by name, --dry-run reports one iteration per instance against the counter you name, and --catalog lists the metrics the host offers.

./build/example/docs_command_line --list
./build/example/docs_command_line --filter='bmWrite' --min-time=0.2
./build/example/docs_command_line --counter=machine/monotonic --dry-run
./build/example/docs_command_line --catalog
printf '%s\n' 'filter=bmWrite' 'min-time=0.2' > "$dir"/run.options
./build/example/docs_command_line --options="$dir"/run.options
SPEEDGUN_FILTER=bmWrite SPEEDGUN_MIN_TIME=0.2 ./build/example/docs_command_line
./build/example/docs_command_line --threads=1,4

User counters

State::setCounter(name, counter) reports a named number for the row the loop is running. The Counter it takes carries a double value, a CounterFlag set and a CounterBase. CounterFlag::RATE divides the value by the primary time of the run in seconds, CounterFlag::ITERATION_INVARIANT multiplies it by the iteration count, CounterFlag::AVG_ITERATIONS divides by that count, CounterFlag::AVG_THREADS divides by the thread count of the run, and CounterFlag::INVERT takes the reciprocal last, after every other flag, of a value that differs from zero: the reciprocal of zero is reported as zero, because a rate of nothing has no reciprocal to print. Flags combine through operator| on the set, so RATE | AVG_THREADS reads as the average per-thread rate; a combined set is how this library spells the single combined flags a Google Benchmark port names kAvgThreadsRate, kIsIterationInvariantRate and kAvgIterationsRate. Each divisor applies on its own, so a run whose primary time is zero skips the rate divisor alone and the iteration flags still apply. CounterBase::K1000 and CounterBase::K1024 choose the suffix, k or Ki, that a human-readable rendering of the column carries. The console prints raw numbers, so the base never divides the value: a counter that holds 64 prints 64 under either base, and CounterFlag::NONE prints the value as it stands.

One benchmark carries at most kMaxUserCounters names, sixteen of them, and a name holds at most kMaxCounterNameBytes minus one bytes, so 31 characters. Both bounds are SG_REQUIRE preconditions of setCounter: a seventeenth name, or a name of 32 bytes, ends the run with the bound named in the message. A name a run opens keeps the flags and base of that call, and a later call for the same name carrying a different pair breaches the same precondition.

The counter columns print after the two time columns, in the order the run opened the names, and the aggregate row carries one statistic line for each counter beside the built-in ones. example/docs/user_counters.cpp runs one family with a counter and a byte rate, and its aggregate lines print under the built-in ones.

Every bound on a counter name and on the number of counters is a precondition of the call that breaches it, so a breach ends the run with the bound in the message. A name keeps the flags and the base of the call that opened it, the column carries the value the body set after the flags are applied, and the aggregate line carries one statistic for each counter.

Throughput

State::setBytesProcessed(bytes) and State::setItemsProcessed(items) report the work one run did and open a rate column for it. Each call takes the total work of the whole run, so a body that works a known amount per iteration passes that amount times state.iterations() after the loop. Each call sets a counter of its own name carrying CounterFlag::RATE, so the value divides by the primary time of the run in seconds. The byte column opens with CounterBase::K1024 and the item column with CounterBase::K1000: the base carries the suffix a human-readable rendering would show, and the console column prints the rate as a raw number. Both are counters of the row like any other: they print in the same fields and carry the same aggregate line.

Each rate column is the total the body reported divided by the primary time of the run, and a run that reports no work prints neither column.

Labels

State::setLabel(label) attaches a word to the row the loop is running. A repetition keeps one label, the last call of that repetition wins, and the report prints it as the trailing field, label=<text>, after the counter columns. A label holding a newline would break the one line per row shape of the report, so the newline is a SG_REQUIRE precondition of the call. The aggregate row carries the label every repetition ended with, and prints no label where the repetitions ended apart.

The label is a trailing field on every row of the family and on its aggregate. The label the last repetition set is the one the row prints. A label carrying a newline breaks the precondition of the call that sets it.

Custom statistics

BenchmarkHandle::addStatistic(name, unit, function) adds one named number to the aggregate row of the family. The StatisticFunc takes the primary time per iteration of the clean repetitions, the same list the built-in statistics summarize, and writes its result through a double reference; a callback that returns false leaves its value out of the row. StatUnit::TIME prints the value in the unit of the row, StatUnit::PERCENTAGE prints it unscaled by the unit. The value prints among the built-in fields in the order the calls came in. The names mean, median, sd, cv, min, max and n belong to the built-in statistics, and a call naming one of them breaches the precondition of addStatistic.

A custom statistic appears on the aggregate row, one value per callback, in the unit the callback names. A callback that returns false leaves its value out of the row. A name a built-in field already uses breaks the precondition of the call that registers it.

Aggregate-only reporting

BenchmarkHandle::reportAggregatesOnly() restricts the report of one family to its aggregate rows: the repetition rows stay measured and stored and never print. BenchmarkHandle::displayAggregatesOnly() trims the console display of one family the same way while the stored result keeps every repetition row, the difference a second output channel reads back. A family with no aggregate row keeps its rows, so neither mode empties a run of output.

Complexity fit

BenchmarkHandle::complexity(BigO) fits the family against the problem size of its instances. BigO::ONE, BigO::N, BigO::N_SQUARED, BigO::N_CUBED, BigO::LOG_N and BigO::N_LOG_N each try one curve, and BigO::AUTOMATIC tries them and keeps the closest. complexity(BigOFun) takes a curve of your own: a double(double) of the size. State::setComplexityN(problemSize) sets the size a run reports, which the fit reads in place of the argument the instance carries.

The fit runs over the instances of the family and reports one pair of rows per fitted quantity: the primary time as time/iter, then each named user counter and each attached metric. The first row of the pair reads BIG_O with the curve and its coefficient, the second reads RMS with the fit error as a percentage. A quantity a member never set gets a SKIPPED row naming the quantity and the reason, and a family with fewer than two instances, or an instance without a positive size, states the reason in place of the rows.

Each curve is fitted by the least-squares closed form k = sum(t * f(N)) / sum(f(N)^2) over the series of the family, where t is the value of one instance and f(N) the shape of the curve at its size. The error row is the root-mean residual t - k * f(N) over the mean of the values, as a percentage. AUTOMATIC fits every curve and keeps the one with the least error, with the constant curve standing when none earns less. A family with too few points to fit states the reason and prints no coefficient.

Execution context lifecycle

An ExecutionContext is one thread the library runs, the inbox that thread reads, and the policy it was created under. A constructor starts that thread: the default one under BLOCK with no pin, the other under the policy you pass. policy() reports that policy for the life of the context.

Three calls close a context, and they close it in this order. requestStop() stands the one stop request that every StopToken of the context reads, and it returns without waiting. drain() waits until the inbox stands empty and the loop stands idle. join() ends the loop and joins the thread, and no work item of the context runs after that call returns. The destructor asks for a context that join() has returned for.

The enqueue of a dispatch() and the stop request race, and the enqueue settles it. A dispatch that finds the inbox open appends its node, and the loop runs that node during drain(). A dispatch that finds the stop request standing refuses its node and completes it STOPPED in that call itself. The loop never takes such a node, so its item never runs. The three calls in order run each accepted node once.

drain() with no stop request standing is a flush. It waits the same way, the accepted nodes have run when it returns, and the loop keeps running, so a later dispatch() runs its node. Work that runs until the stop request stands reads stopRequested() on the token of its WorkContext and returns once that token reads true.

Two calls share one precondition: the calling thread is not the thread of that context's loop. drain() from that thread would wait on the work that thread must finish, and join() from it would wait on itself.

The caller owns its node. WorkNode lives in caller storage, and the caller keeps it alive until state() reads DONE or STOPPED. A refused node reaches STOPPED in the dispatch that refused it, and the loop completes a node it accepted, so one of the two settles the state.

Work runs on the thread of the context it was dispatched to. The dispatches of one thread run in the order that thread made them, and the inbox decides between two threads. Work dispatched from inside a running item runs after that item returns, on the same context.

Three calls close a context, the destructor asks for the joined state, and each accepted node runs once. A node a stopped context refused reads STOPPED without running. A context you start yourself outlives the benchmark run, because speedgunMain returns while its work runs, and these three calls end it.

The chunk rule

A chunk holds the least count of iterations whose time reaches 100 times the cost of one sample action, which keeps a sample under 1% of the window it bounds. The first attempt of a fixed-count run has no measured iteration time to calibrate from, so its chunks hold one iteration each and the next attempt of the instance calibrates from the time the first measured. A pause interval inside a chunk nets out of that chunk's time and of no other chunk's.

A point reads the nearest rank of the sorted chunk times: the value at position ceil(p * n / 100), counting from one, over the n chunk times the run holds. The point needs a least count of chunks before it answers at all, and that count is ceil(100 / (100 - p)).

}

The shape of the document

The root object carries schemaVersion, speedgun and benchmarks. The speedgun object carries the library version and the build type of the build that ran. benchmarks holds one entry per benchmark, in registry order, and each entry holds its name, suite, case, outcome, reason, time unit, percentile points, contexts, noise warning, rows, labels and statistics, beside the pass disclosure metricMethod, passCount, passSpread and spreadWarning. One row per repetition carries its iteration count, its two time columns, its metric and counter columns, its statistics, its percentile cells, its fit and its raw chunk columns. Each metric column of a row carries pass, the index of the pass that measured the value. docs/schema/report-v1.json states the whole shape.

The version rule

schemaVersion names the shape of the document. A document whose major stands at 1 loads, whatever its minor says; a later major is refused, and the refusal names the version the document carries. A run writes 1.4, the shape that added the hunt keys; a 1.0 document, which carries neither the hunt keys nor the pass fields, loads through the same rule.

The null rule

A percentile the chunk count cannot answer stands as null, the file form of the not available the console prints. reason, label, noiseWarning, counterDisclosure and fit stand null where the run carries none, and a statistic whose sample set stands empty answers null for every quantity. passSpread and each metric column's pass stand null where fewer than two passes measured the run.

The raw column rule

raw.columns holds one array per reported quantity, in the order the percentile lines read them: the primary time, the time column the primary is not, then each metric. Each array holds chunkCount values in the order the run closed the chunks. A percentile line reads its own sorted order over those values. The key stays out of the row when the run captured nothing.

The loader rule

loadReport(path) returns the run's own values, or an error naming the JSON pointer of the field it could not read. The loader checks the fields it reads; it does not validate the document against the schema file, which stands as the gate's oracle.

The no-date rule

No key of the document names a date, a time, a host or a process id. The file is a function of the values the run measured, so two runs of one build write the same bytes and a diff of two runs shows only what changed in the run.

Regression gate

Two report documents go in and one verdict comes out. --compare names the baseline document and the contender document, split at the first comma, and the mode loads both through loadReport; it runs no benchmark and reads no clock. --compare-rule adds one rule and repeats in the order given, and with no rule the gate applies one: the median primary time at five percent relative. --compare-strict makes a NOISY row fail the run while the word that row prints stays NOISY. --filter scopes the pair the way it scopes a run.

  --compare=test/data/gate_ok_base.json,test/data/gate_ok_contender.json
./build/example/first_benchmark \
  --compare=test/data/gate_fail_base.json,test/data/gate_fail_contender.json

The table prints one line per input naming its path, its speedgun version and its schema version, then a header and one row per benchmark under one rule: the baseline value, the contender value, the change in percent, the change in the unit the baseline report declares, and the state word. The rule grammar

<rule>      ::= <value> [ @ <aggregate> ] : <direction> : <threshold> [ : <filter> ]
<value>     ::= time | real_time | cpu_time | p <point>
              | counter : <label> | metric : <label> | stat : <label>
<aggregate> ::= median | mean | min | max
<direction> ::= lower | higher
<threshold> ::= <percent>% | abs = <number> | <percent>% , abs = <number>
<filter>    ::= any text, the rest of the rule text

The fields run in that order. time reads the primary column, real_time and cpu_time read one column by name, p<point> reads one percentile cell, and the three prefixed names read the column or the statistic their label names. A label ends at the first unescaped colon, and \: , \, , \@ and \\ stand inside it. The @ suffix names one aggregate and defaults to median for a name the report holds as a statistics record; a written suffix on a percentile cell or on a statistic is a fault. The direction word is required. A threshold carries a percent, an abs= number, or the two in that order, the number standing in the stored unit of the value. The filter is a regular expression over the full instance name, matched the way the batch filter option matches.

parseCompareRule is the public call behind that parse, and compareReports takes the rules with two loaded reports and one CompareOptions value, so a program can drive the comparison the options drive. The settings struct carries strict, the same setting --compare-strict answers, and a later setting joins it with the call's signature unchanged.

The state words

An entry is one benchmark under one rule, and it carries one of seven words.

WordThe row that prints it
OKthe change sits inside the rule's threshold
REGRESSEDthe change moves against the direction past the threshold
IMPROVEDthe change moves with the direction past the threshold
NOISYthe row cannot carry a verdict
ADDEDthe name stands in the contender alone
REMOVEDthe name stands in the baseline alone

lower means a smaller value is better, so the change a lower rule watches is the positive one, and a rule with both thresholds written regresses a row only when both are exceeded. A NOISY row prints reason= naming every condition that fired: a noise warning the report carries, a coefficient of variation past the relative threshold, a sample standard deviation past the absolute threshold, or a metric running ratio below one. That row fails the run only under --compare-strict. ADDED, REMOVED and SKIPPED print n/a in their value cells and never fail the run.

Multi-pass collection

A metric set that needs more PMU events than the processor counts at once is a supported case. A pass is one collection round. It opens the events of the columns assigned to it, runs every repetition, and closes with its own readings. The harness splits the set into passes, runs the benchmark once per pass, and merges the passes into the usual one row per instance. The split and the merge sit outside every timed window.

Two published facts drive the split: Object::programmableCounters states how many programmable counters one context can hold open on one event source, and a loaded metric states how many events its column needs. The planner reads both before the first timed window and opens no counter.

--metric-method=auto, --metric-method=passes and --metric-method=multiplex choose the method, and metricMethod on the handle carries the same three values. auto is the default. The command line wins over the handle, and a repeated option keeps its last word. A word outside the three prints one line and ends the run with status 2.

example/docs/metric_passes.cpp makes that request from the registration side, on the handle the over-limit set was attached to:

#include "speedgun-ng/benchmark.hpp"

A run that measured more than one pass prints one disclosure line under its rows. A caller that forced a method sees the same line for one pass:

<name>                      passes  method=passes  count=2  spread=11.1%
warning: pass spread 11.1% exceeds 5%

method= names the method the run settled to, count= the passes it measured, and spread= the relative spread of the time per iteration across those passes. A spread above 5% brings the warning line with it, and the warning changes no value and no exit status. When more than one pass ran, each metric column gains a pass=<index> token after its gap= field, naming the pass that measured the value. A one-pass run of the default method prints no line, and its report names AUTO with a count of zero, a null spread and a null pass on every metric column.

The split rule

The planner takes the PMU columns of the run in request order: the metric columns in the order addMetric attached them, then the user-counter columns in the order --counter opened them. Each column joins the first pass that still holds all of its events within every source limit, and a column with no such pass opens a pass of its own.

The events of one column stay in one pass, because a pair split across two windows has no common interval to fold. A column wider than the limit takes a pass of its own and runs oversubscribed: the kernel rotates its events over the counters, and the ratio= field discloses the fraction of the enabled time the value covers. The two machine clock leaves of the spine (machine/monotonic and the CPU leaf the family selected) ride every pass and count against no limit, because they consume no programmable counter. The same columns, method and limits give the same passes on every run.

One calibration runs before the first pass, and every pass takes the iteration count it produced, so the passes measure the same amount of work. Every pass runs the repetitions the family and the run control ask for, on the same execution contexts as the other passes. In a threaded run every context finishes one pass before any context opens the next.

The merge rule

The merge publishes one result of the usual shape: one row per instance and repetition, in the column order the run fixed before the split. Each metric column and each user-counter column carries the values of the pass that measured it. The time columns, the overhead floor, the endpoint samples, the CPU-time column and the percentile columns of the primary time come from pass 0, the reference pass. The percentile columns of a metric come from the pass that measured that metric. A value whose measuring pass folded a gap keeps the gap disclosure, and a refused metric keeps its refusal kind. The merge moves the values the passes folded, and it publishes no value a pass left unmeasured.

The pass spread

The spread is the maximum minus the minimum, divided by the median of the reference time per iteration of the passes, as a percentage. The primary time column of each pass's reference row supplies that pass's figure. The median of an even count is the lower of the two central values, and the formula takes no average. One pass carries no spread. A median of zero answers spread=not available. Pass times of 100 ns, 108 ns and 112 ns through a median of 108 ns give a spread of 11.1%, and the warning line follows.

The merged result carries the same three values as published fields, BenchmarkResult::metricMethod, passCount and passSpread, so a consumer reads what the line prints.

A host that publishes no limit

An event source the counters library cannot answer for publishes no limit. Such a host keeps the single oversize plan and the kernel rotation of it under auto and under a forced passes alike, and the disclosure line names method=multiplex. No spread appears, because one plan measured the run, and every column keeps its ratio=, scaled= and gap= fields. A missing limit stays a missing fact: the run completes and discloses the method it used.

A run whose metric set is wider than the counters measures the set in rounds and still reports one row per instance: each metric value comes from a pass that counted it inside the limit, the times come from the first pass, and the line under the row states the method, the pass count and the spread between the passes. --metric-method pins one method for a scripted comparison of the two. Hunter mode

Hunter mode puts a wide catalog event set on one benchmark and ranks the events by how far each one stands out of the run. --hunt turns it on and selects the events, and seven --hunt-* options shape the measurement. The hunt drives the pass loop described above, so it opens no second counter path. Its lines print on stdout under the hunt: prefix, after the benchmark tables of the run. A value outside the range its option states prints one line naming it on stderr and ends the run with status 2.

A run with no --hunt prints no hunt: line and writes no hunt key. Its console bytes and its document are the bytes they were before hunter mode existed.

events= counts the planned columns and passes= the passes of the plan. method= names the settled collection method, and estimate= carries the plan's own figure in nanoseconds: the real-time column of one window of the plan's shape (ResultRow::timePerIterationNs), which the hunt measures by running that window ahead of the run, weighed against the passes of the plan. The figure is the counted span the run's own rows price, so the seat of the leaves and the opening of the window stand outside it, and no file of this layer reads a clock to get it: the time source rule reserves the monotonic clock for the counters layer, whose measurement this figure is. A hunt that measures no pass prints estimate=not available: the entry of a dry run runs nothing to measure, and so does a host that refuses the seat of the pass. A seconds budget is read against the estimate, which is why the estimate decides the two-stage run. A plan the budget splits names both stages, stage1= and stage2=, each with the events it measures, and a plan of one stage names none. The rank lines carry the rate under the label of the norm in force, instr=, cycle= or iter=. A skipped line names the address and the kind of the refusal in the words the --catalog listing prints. The summary denominator counts the planned events plus the refusals that kept an event out of the plan, and its numerator counts the events that produced at least one usable sample.

A host that refuses every event prints the plan line, the skipped list and the summary with events=0/N, and the run ends with status 0. A group open that refuses mid-run retries its events one at a time; an event that still refuses joins the skipped list, and the run still ends with status 0. Beside --dry-run every pass runs one iteration, so each column reaches the table with one sample, a cv of 0.00 and mark=unrepeated.

The norm and the rank

--hunt-norm=instr divides an event count by the instructions of the same window, cycle by the cpu-cycles of the same window, and iter by the iteration count of the attempt. A rate reads per thousand of its denominator, and per iteration under iter. A window that disclosed a gap contributes no rate, and so does a window whose denominator read zero.

Each anchor rides every pass of its own device, so a device that lacks one of the two anchors leaves the whole plan to measure under iter. The plan line then carries normalized=iter, and the rate column reads iter=. An explicit word whose anchor discovery refused for the hunt is a refusal, and it ends the run with status 1, and the block states the shape of the output:

hunt: the hunt norm cycle names the anchor 'cpu/cpu-cycles', which discovery refused for the hunt of 'cpu/l2_lines_out.any_core'

rate is the median of the per-window rates and cv is the coefficient of variation of those rates, as a percentage. --hunt-rank=rate orders the table by rate descending and --hunt-rank=cv by cv ascending, with the catalog address as the tie break. At most --hunt-top rows carry a rank, numbered from 1 with no gap. Every other row prints rank - and a mark=: noisy for a cv above the --hunt-noise percent, unrepeated for an event with one sample, beyond-top for a rankable event the size of the table left out. One sample carries no deviation, so it is never noisy.

The budget

With no --hunt-budget one stage measures every planned event at --hunt-repeats repetitions. A budget splits the run into two: a first stage over every planned event at one repetition, then a second stage over the first 3 x --hunt-top planned events, or over the whole plan if it holds fewer, at --hunt-repeats. A budgeted run measures everything once and the top set again. A plan whose estimate does not fit the budget drops the second stage whole. The budget prints in the unit it was given, budget=120s or budget=8p, on the plan line and on the summary.

The stated collection method

The plan settles its method from the published counter limits: PASSES if a device it needs publishes one, MULTIPLEX if no needed device publishes one. --metric-method states a method outright, and the stated word outranks that settlement. The plan hands that word to the pass loop, the plan line prints the stated word in method=, every rank row carries the word multiplexed if the settled method is MULTIPLEX, and both method keys of the document carry the stated word. --hunt with --metric-method=multiplex therefore measures every event in one oversubscribed window and says so in all three places.

The two hunt objects

Every benchmark entry of a hunt run carries a hunt object as its last key, with method, pass_count, top, retried_passes, entries and skipped. method is the settled method, pass_count counts the passes the run measured with the passes a retry appended included, top is the --hunt-top value, and retried_passes counts the passes whose group open refused. Every item of entries carries address, rate, cv, noisy, multiplexed and rank, the ranked events first in rank order and the excluded ones after them in address order, each rank of an excluded event standing null. Every item of skipped carries address and kind, the two figures one refused event states: the stage an event stood in belongs to the plan, which stages already prints. A run with no hunt writes no hunt key in any entry.

The document closes with one run-level hunt object after the benchmarks array, holding selection, norm, rank, top, noisePercent, repeats, seed, budget, passes, method, events, stages, estimate_ns, planned_events, ran_events and stage_two_events. selection repeats the text the option carried, and a @file selection arrives here as the deduplicated address lines it read. events holds every planned address in plan order, and stages holds one item per stage that ran, each with first, count and repeats. budget stands null with no budget and estimate_ns stands null when the hunt timed no pass. ran_events counts the events that produced a usable sample and stage_two_events the events the second stage re-measured.

The words these keys take are the words the options take: method is AUTO, PASSES or MULTIPLEX, norm is instr, cycle or iter, the ranking key rank is rate or cv, and a kind is permission-blocked, not-encodable, absent, scope-refused or gap.

The library surface

speedgun-ng/hunt.hpp carries the surface the options drive. runHunt(benchmark, options, calibrationNsPerPass) plans, measures and ranks one hunt for a registered benchmark. planHunt(events, limits, anchors, options, calibrationNsPerPass) answers the plan over the events, the per-device limits and the anchors, and rankEvents(collected, options, method) ranks samples the caller already holds under the method it hands. None of the three opens a window: every time and count figure in their records comes from an argument. EventCatalog expands a selection text against the catalog and splits it into the events to plan and the events discovery refused.
