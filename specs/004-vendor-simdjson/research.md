# Research: Vendor simdjson as a Private, Pinned Submodule

**Feature**: 004-vendor-simdjson | **Date**: 2026-09-23
**Status**: All NEEDS CLARIFICATION resolved (0 remaining).

Every fact below was verified on 2026-09-23 against the simdjson tag `v4.6.11` (annotated tag: tag object `e153ffadd9ae29b00c90bedc76f65d25a993d2b5`, commit `f5de14f09256982933af2849beb43778bd421ca7`, re-confirmed via `git ls-remote`), against upstream master `6913ee1a17a57d23a2e9f484d8e04e96cd43ecab` (project VERSION 4.6.1), and against the speedgun-ng tree as it stands. Each decision names the requirements it settles. The hwloc import (specs/003-vendor-hwloc) is the shape precedent; where simdjson forces a different mechanism, that divergence is the research contribution here.

## Phase 0 Findings

### R-001: Ingestion mechanism = submodule + `add_subdirectory` of a native CMake library; `ImportAutotoolsSubmodule` stays unused

- **Decision**: simdjson enters as a git submodule at `external/simdjson` (settled path, spec assumption: the root convention for every vendored dependency, matching `external/hwloc`). The build ingests it through `add_subdirectory(external/simdjson <binary-dir> EXCLUDE_FROM_ALL)` with simdjson's own options set in a scoped bracket (R-006). The `cmake/ImportAutotoolsSubmodule.cmake` module (written for the autotools hwloc tree) is not loaded here.
- **Rationale**: FR-011 fixes `add_subdirectory` with `EXCLUDE_FROM_ALL`; the spec assumption records simdjson as a native CMake library needing no autotools bootstrap. Verified at master: `CMakeLists.txt:1` declares `cmake_minimum_required(VERSION 3.14)`, the library target is created directly by `add_library(simdjson ${SIMDJSON_SOURCES})` (`CMakeLists.txt:206`), and `cmake_minimum_required`, `add_library`, and the whole build are CMake-native. No `configure`, `Makefile.am`, `autogen.sh`, or host autoconf/automake/libtool/patch is introduced. This is strictly less host tooling than the hwloc ingestion needed (specs/003 R-011).
- **Alternatives considered**:
  - *FetchContent / registry distribution*: rejected by the spec (vendoring or nothing, Scope boundaries).
  - *The `ImportAutotoolsSubmodule` copy-and-bootstrap path*: rejected: it exists to run `autogen.sh` and an out-of-tree `configure` in a copied autotools tree; simdjson has neither. Reusing it would add machinery with no job (constitution X.2).
  - *Amalgamated `singleheader/simdjson.{h,cpp}` checked into the tree*: rejected: the spec requires the pinned submodule as the source of truth (FR-001); the amalgamation is a build product.

### R-002: Version assertion = `static_assert` on the `simdjson::SIMDJSON_VERSION_{MAJOR,MINOR,REVISION}` enum constants

- **Decision**: The wrapper TU asserts `static_assert(simdjson::SIMDJSON_VERSION_MAJOR == 4 && simdjson::SIMDJSON_VERSION_MINOR == 6 && simdjson::SIMDJSON_VERSION_REVISION == 11, "...expected simdjson 4.6.11...")`. The identifiers come from `include/simdjson/simdjson_version.h` (generated by `tools/release.py`), pulled in by `#include <simdjson.h>` (`include/simdjson.h:41`). An optional cross-check `static_assert(std::string_view{SIMDJSON_VERSION} == "4.6.11", "...")` is admissible because the string macro is a clean dotted triple at the tag.
- **Rationale**: FR-003 demands exactly 4.6.11 with a readable diagnostic, and rejects any 4.6.x patch. The verified structure at `include/simdjson/simdjson_version.h` (tag `v4.6.11`): `#define SIMDJSON_VERSION "4.6.11"` plus, inside `namespace simdjson`, `enum { SIMDJSON_VERSION_MAJOR = 4, SIMDJSON_VERSION_MINOR = 6, SIMDJSON_VERSION_REVISION = 11 };`. The load-bearing fact for the design: MAJOR/MINOR/REVISION are **enum constants**. `#if` reads only preprocessor macros, so it cannot see them; `#if SIMDJSON_VERSION == "4.6.11"` is invalid (preprocessor arithmetic cannot compare strings). A `static_assert` over the three enum constants is the compile-time gate, and the compiler prints the offending values in the failing expression, so the diagnostic identifies both the expected version (the message text) and the mismatch (the values). The triple rejects 3.x, 4.5.x, 4.7+, and any 4.6.x patch (REVISION != 11).
- **Alternatives considered**:
  - *`#if`-based numeric check*: rejected: simdjson exposes no `#if`-comparable numeric version macro; the identifiers are enum constants. This is the trap the design avoids.
  - *Assert `std::string_view{SIMDJSON_VERSION} == "4.6.11"` alone*: admissible as a cross-check, kept secondary: the enum triple is the primary gate and matches the hwloc precedent's triple shape (specs/003 R-002). Unlike hwloc (whose pinned VERSION string was `2.14.0rc2-git` and rejected a string-equality assert), simdjson's pinned string is exactly `4.6.11`, so both readings pass.
  - *Runtime version comparison*: rejected: no runtime version accessor exists (R-003); FR-003 says compile-time.

### R-003: Link-proof symbol = `simdjson::get_active_implementation` (no runtime version accessor exists)

- **Decision**: The wrapper TU holds `[[maybe_unused]] constinit auto const link_proof = &simdjson::get_active_implementation;` (with `[[gnu::used]]` under `__GNUC__`, exactly as `source/hwloc/hwloc_gate.cpp` does). Taking the address, without calling, forces an undefined reference to the real exported symbol; the merged vendored member resolves it (FR-007, SC-009).
- **Rationale**: FR-007 requires `nm` on the built static archive to show simdjson objects pulled in by the wrapper's reference. `simdjson::get_active_implementation` is declared `extern SIMDJSON_DLLIMPORTEXPORT internal::atomic_ptr<const implementation>& get_active_implementation();` (`include/simdjson/implementation.h:226`) and defined at `src/implementation.cpp`; it is a genuine out-of-line symbol in the archive. The `SIMDJSON_DLLIMPORTEXPORT` macro is empty on Linux/macOS (R-007), so on ELF the symbol is plain. `constinit` forbids a startup initializer, keeping the wrapper at zero runtime lines (coverage gate).
- **Alternatives considered**:
  - *`&simdjson::version` / `&simdjson::version_string` / `simdjson_version()`*: rejected: none of these exist. Verified absent from `include/` and `src/` at master, v3.12.0, v2.0.0, v1.0.0, v0.9.7. simdjson exposes its version compile-time only (R-002); there is no addressable version symbol.
  - *`reinterpret_cast` of a function pointer to `void*`*: rejected: constitution X.2 permits a cast only where a contract makes it sound; the hwloc wrapper avoided it by using a typed `constinit` function-pointer reference, and simdjson matches that (no cast, no P2 exception).

### R-004: Install and developer-mode suppression = explicit `SIMDJSON_INSTALL=OFF`; developer mode left unset; `EXCLUDE_FROM_ALL`

- **Decision**: In the scoped bracket (R-006), set `SIMDJSON_INSTALL OFF`. Do not set `SIMDJSON_DEVELOPER_MODE`. `add_subdirectory(... EXCLUDE_FROM_ALL)`.
- **Rationale**: FR-011 and FR-014. The entire install/export/pkg-config block sits under `if(SIMDJSON_INSTALL)` (`CMakeLists.txt:395`, block through L476); turning the switch off means simdjson defines zero install rules, so `cmake --install` copies nothing of simdjson into `CMAKE_INSTALL_PREFIX` (SC-002). The load-bearing subtlety: when simdjson is a subproject, `SIMDJSON_INSTALL` defaults to `${BUILD_SHARED_LIBS}` (`CMakeLists.txt:196`), so it is ON in a shared parent build. The repository's own `shared-audit` CI job builds with `BUILD_SHARED_LIBS=ON` (`.github/workflows/ci.yml:167`), which under the default would flip simdjson install ON and leak it into the prefix. Setting `SIMDJSON_INSTALL OFF` explicitly closes that footgun for every configuration. Developer mode: `SIMDJSON_DEVELOPER_MODE` is declared only inside simdjson's `if(is_top_project)` block (`CMakeLists.txt:190-197`); as a subdirectory it is never declared, so it stays undefined and evaluates false, and `if(NOT SIMDJSON_DEVELOPER_MODE) return()` (`CMakeLists.txt:502`) ends the file after the library, so tests, benchmarks, examples, fuzzers, tools, and singleheader regeneration are structurally absent. `EXCLUDE_FROM_ALL` keeps the vendored target out of the default `all` target while the link edge still builds it (FR-011).
- **Alternatives considered**:
  - *Rely on the `SIMDJSON_INSTALL` default being OFF*: rejected: it tracks `BUILD_SHARED_LIBS`, which the shared-audit job sets ON; the privacy contract (FR-014, SC-002) cannot rest on a default that a build variant flips.
  - *Set `SIMDJSON_DEVELOPER_MODE OFF` explicitly*: rejected as unnecessary: the option is not declared for a subproject, so an explicit OFF adds a cache entry for a value that is already the effective one; leaving it unset matches the library-only consumer path simdjson documents (HACKING.md: a consumer "only get[s] the library targets").
  - *`SIMDJSON_SINGLEHEADER OFF`*: the option is top-level-only and harmless here; singleheader generation lives behind the developer-mode return, so it never runs. Not set.

### R-005: Force simdjson static under a shared speedgun-ng = scoped `BUILD_SHARED_LIBS=OFF`

- **Decision**: The scoped bracket sets `BUILD_SHARED_LIBS OFF` for the `add_subdirectory` call. simdjson then builds a static archive (`libsimdjson.a`) regardless of how speedgun-ng itself is configured; the enclosing speedgun-ng target's own `BUILD_SHARED_LIBS` value is unaffected (the bracket is a function scope, R-006).
- **Rationale**: FR-007 (static, internal linkage) and FR-016/SC-004 (a shared speedgun-ng resolves no simdjson object). `add_library(simdjson ${SIMDJSON_SOURCES})` (`CMakeLists.txt:206`) carries no type keyword, so its library type follows `BUILD_SHARED_LIBS`. Under the shared-audit job (`BUILD_SHARED_LIBS=ON`), an unscoped simdjson becomes a shared `libsimdjson.so`; a shared speedgun-ng linking it would gain a runtime dependency, and `ldd` on the installed `libspeedgun-ng.so` would name `libsimdjson.so`, violating SC-004. Pinning the vendored build static keeps every configuration's privacy story identical: the archive's members are absorbed at speedgun-ng link time (R-009), never a separate object file.
- **Alternatives considered**:
  - *`SIMDJSON_BUILD_STATIC_LIB=ON` and link `simdjson::simdjson_static`*: rejected: that option adds `simdjson_static` alongside the `BUILD_SHARED_LIBS`-typed `simdjson` (`CMakeLists.txt:35`, L240-249); in the default static speedgun-ng build both become identical static archives and simdjson warns. Scoping `BUILD_SHARED_LIBS OFF` yields exactly one static archive in every configuration.
  - *Let simdjson follow the parent's `BUILD_SHARED_LIBS`*: rejected: it produces a `libsimdjson.so` in the shared build, the exact SC-004 runtime-dependency leak the contract forbids.

### R-006: The exemptions hwloc got for free must be built explicitly = a scoped variable-reset bracket around `add_subdirectory`

- **Decision**: One helper function wraps the `add_subdirectory(external/simdjson ...)` call. Inside it, before the call, the following variables are set; the function scope prevents them from leaking to the rest of the build:
  - `CMAKE_CXX_FLAGS ""` (drop the parent strict warning set, `-Werror`, and hardening for the vendored compile),
  - `CMAKE_CXX_FLAGS_SANITIZE ""` and `CMAKE_CXX_FLAGS_COVERAGE ""` (no sanitizer, no `--coverage`),
  - `CMAKE_CXX_CLANG_TIDY ""` and `CMAKE_CXX_CPPCHECK ""` (no static analysis of vendored code),
  - `CMAKE_CXX_VISIBILITY_PRESET hidden` (R-007),
  - `BUILD_SHARED_LIBS OFF` (R-005), `SIMDJSON_INSTALL OFF` (R-004).
  Targets created inside a function persist to the caller's build system (target-creating commands are not confined by function scope), so the resulting `simdjson::simdjson` handle is usable by `target_link_libraries` outside the function.
- **Rationale**: FR-009 and FR-010. This is the central divergence from hwloc. An `ExternalProject` autotools child inherits none of the parent's compile flags, tidy, cppcheck, or sanitizers; a CMake `add_subdirectory` child inherits all of them through the directory-scope variables `CMAKE_CXX_FLAGS`, `CMAKE_CXX_FLAGS_<CONFIG>`, `CMAKE_CXX_CLANG_TIDY`, and `CMAKE_CXX_CPPCHECK`. Without the bracket: the sanitizer preset (`CMAKE_CXX_FLAGS_SANITIZE`, `CMakePresets.json:130`) instruments the vendored archive (FR-010 violation); the coverage preset injects `--coverage` into it; the strict `-Werror` set (`CMakePresets.json:61`) fails simdjson's own sources; and tidy/cppcheck analyze vendored code (FR-009 violation). Neutralizing these in a function scope realizes the spec-mandated exemptions that are structural for hwloc and constructed for simdjson. The coverage *extraction* whitelist (`cmake/coverage.cmake:50-51`: `include/speedgun-ng/*`, `source/*`) already keeps vendored paths out of the report, but blanking `CMAKE_CXX_FLAGS_COVERAGE` additionally stops instrumentation from being emitted at all, so the exclusion is not dependent on the extraction step alone. Mixing sanitizer-instrumented callers with an uninstrumented static dependency is supported by ASan/UBSan; instrumented speedgun-ng code still gets out-of-bounds detection on simdjson-allocated memory (the identical rationale specs/003 R-008 records).
- **Alternatives considered**:
  - *Per-target `set_target_properties` clearing after `add_subdirectory`*: rejected for the sanitizer/coverage flags: those come from `CMAKE_CXX_FLAGS_<CONFIG>`, applied at generation from the directory scope; a post-hoc property edit cannot subtract them. The scope reset is the one place the values can be neutralized before the child targets are generated.
  - *Editing the presets to omit simdjson*: rejected: the presets are shared by every target; narrowing them to exempt a vendored path would weaken the gates for all code (constitution VIII).
  - *`ExternalProject`/`FetchContent` for simdjson to inherit nothing, as with hwloc*: rejected by FR-011 (add_subdirectory), and it re-adds the download/patch machinery the spec refuses.

### R-007: Symbol privacy = `CXX_VISIBILITY_PRESET hidden` baked at simdjson compile time; no upstream prefix exists

- **Decision**: Set `CMAKE_CXX_VISIBILITY_PRESET hidden` in the scoped bracket (R-006) so simdjson's sources compile with `-fvisibility=hidden`; each symbol is stamped `STV_HIDDEN` in its `.o`. Static absorption (R-009) keeps those members inside `libspeedgun-ng.a`. No `--exclude-libs` link-time option is added.
- **Rationale**: FR-016 and SC-004. Verified: simdjson applies no `__attribute__((visibility("default")))` anywhere (repo-wide grep empty); `SIMDJSON_DLLIMPORTEXPORT` is Windows-only and expands to nothing on ELF (`include/simdjson/common_defs.h`, non-Windows branch); simdjson never sets `CXX_VISIBILITY_PRESET` or `-fvisibility` itself, and `CMakeLists.txt` carries the upstream comment `# FIXME: symbols should be hidden by default` beside `WINDOWS_EXPORT_ALL_SYMBOLS YES`. Therefore, on ELF, simdjson symbols are `STV_DEFAULT` purely by compiler default and leak into a shared library's `.dynsym` unless the vendored objects compile hidden. Because simdjson adds no default-visibility attribute and no escape hatch on Linux/macOS, `-fvisibility=hidden` reliably stamps every vendored symbol hidden. Visibility is a compile-time, per-object property baked into the archive members: a hidden member linked into a `.so` is not promoted to `.dynsym` (SC-004), while a static archive has no `.dynsym` at all, so the static path exports nothing regardless.
- **Alternatives considered**:
  - *Rely on speedgun-ng's own `CXX_VISIBILITY_PRESET hidden` (`CMakeLists.txt:38-39`)*: rejected: that preset governs speedgun-ng's own compilation and does nothing for simdjson objects compiled by the vendored subdirectory; visibility must land on the simdjson compile.
  - *`-Wl,--exclude-libs,ALL` at the shared link*: rejected for this feature: it is a correct belt-and-suspenders for a pre-built default-visible archive, but here the objects are compiled in-tree with the hidden preset, so the leak is closed at its source. Adding a repo-wide `--exclude-libs` would touch the shared-linker flags of every target (constitution VIII gate surface) to solve a case already handled at compile time. Revisit only if a future build consumes a pre-built simdjson.
  - *Symbol prefix (the hwloc `sg_` route, specs/003 R-003)*: rejected: simdjson has no prefix or namespace-rename mechanism (verified: `namespace simdjson` is hardcoded, no `SIMDJSON_NAMESPACE` define, no inline ABI namespace). Collision removal therefore rests entirely on hidden visibility plus static absorption, exactly the spec assumption states.

### R-008: Wrapper include under the strict gate set = vendored headers as SYSTEM, and `clang-tidy`/`cppcheck` header scope excludes `external/`

- **Decision**: Two coordinated edits carry FR-009/FR-013 for the wrapper:
  1. After `add_subdirectory`, promote simdjson's interface include directory into its `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES`, so the wrapper compiles `<simdjson.h>` via `-isystem`. Diagnostics originating inside the vendored header are suppressed; the wrapper's own lines stay fully compiled under the strict `-Werror` set.
  2. Narrow the `clang-tidy` header-filter in `CMakePresets.json:43` (`^${sourceDir}/`) so it does not match `external/`, keeping vendored headers reached through the wrapper out of tidy's reported findings; cppcheck is directed to skip vendored paths for the wrapper TU.
- **Rationale**: FR-009 (vendored exempt from tidy/warning gates) and FR-013 (simdjson headers includable only from `source/`). The wrapper TU `source/simdjson/simdjson_gate.cpp` belongs to the speedgun-ng target, which carries the strict warning set with `-Werror` and, in the `ci-ubuntu` preset, clang-tidy and cppcheck. Unlike hwloc's clean C header, `<simdjson.h>` is a heavy C++ umbrella header whose internal lines are not written to the project's `-Wconversion -Wshadow -Wold-style-cast ... -Werror` baseline: a plain include fails the wrapper compile, and the header-filter regex `^${sourceDir}/` matches `external/simdjson/...` (it is in-tree), so clang-tidy would descend into vendored headers and report them. Making the include SYSTEM suppresses compiler diagnostics from the header (the `-isystem` semantics) while the wrapper's own trivial lines (a `static_assert` and an address-of) remain gated; excluding `external/` from the header-filter realizes the FR-009 exemption for static analysis. This is the concrete mechanism the spec assumption ("the plan records the concrete mechanism") requires.
- **Alternatives considered**:
  - *`add_subdirectory(external/simdjson SYSTEM ...)`*: rejected: the `SYSTEM` keyword needs CMake 3.25, above the project floor of 3.20 (`CMakeLists.txt:1`, `CMakePresets.json:3-7`); `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES` has existed since CMake 2.8 and does the job at the floor.
  - *Compile the whole wrapper TU with `-w`*: rejected: that turns off warnings for the wrapper's own lines too, contradicting FR-009's "speedgun-ng code that calls simdjson is held to all of them"; the SYSTEM include suppresses only header-originated diagnostics.
  - *Wrap the include in `#pragma GCC diagnostic ignored "-Wall"`*: considered, kept as a fallback; rejected as the primary because it enumerates warning families incompletely and does not address clang-tidy, whereas the SYSTEM include plus header-filter cover compiler and analyzer together.

### R-009: Static builds merge `libsimdjson.a` into `libspeedgun-ng.a`; shared builds absorb it PRIVATE

- **Decision**: When `BUILD_SHARED_LIBS=OFF` (the repo default, `cmake/variables.cmake:9`), a post-build step merges the vendored archive members into the speedgun-ng static archive through the archiver (`ar -M` `ADDLIB` on GNU ar, `llvm-ar -M` on current macOS), referencing `$<TARGET_FILE:simdjson>`. When `BUILD_SHARED_LIBS=ON`, the library links `simdjson::simdjson` PRIVATE; the hidden-visibility objects (R-007) keep every simdjson symbol out of the `.dynsym`. The link edge is wrapped in `$<BUILD_INTERFACE:simdjson::simdjson>` so the vendored name never enters the exported target set (the pattern `CMakeLists.txt:88` uses for `hwloc_vendor`).
- **Rationale**: FR-007 and SC-009. A static archive does not absorb members of another archive at creation, so the merge is what makes `nm libspeedgun-ng.a` list simdjson objects with the gate object's reference resolved (SC-009), and it is the same slurping pattern specs/003 R-010 established. The merge also answers a consumer-facing correctness fact: a static library's PRIVATE link dependencies do not survive installation, so a thin `libspeedgun-ng.a` would leave the gate's `simdjson` reference unresolved for any consumer that pulls the gate object; a merged archive is self-contained while its package files name nothing foreign (FR-015). For the shared build, PRIVATE absorption plus hidden objects satisfies FR-015 and SC-004 (the installed `.so` carries no simdjson link-interface entry and no simdjson runtime dependency).
- **Alternatives considered**:
  - *Thin static archive plus a hidden `INTERFACE_LINK_LIBRARIES` carry-over*: rejected: it leaks simdjson paths into the installed `speedgun-ngTargets.cmake` (FR-015) and pushes a disguised dependency onto consumers (specs/003 R-010 reasoning).
  - *`$<TARGET_OBJECTS:simdjson>`*: rejected: it enumerates object files, but the archive boundary and ordering are cleaner through the imported-style merge the hwloc path already proves.
  - *Skip the merge for static builds*: rejected: it fails SC-009 and leaves the future internal serialization consumer (the spec's named downstream feature) with an unresolved reference.

### R-010: Audit and gate wiring = reuse the existing jobs and scripts; two build-file edits carry the new dependency

- **Decision**:
  1. `tools/dbc/dependency_scan.sh` gains `simdjson` to its vendored-private classifier (the branch that already whitelists `hwloc_vendor`, lines 94-97), so the new PRIVATE link on `speedgun-ng_speedgun-ng` classifies as vendored-private and the existing `dbc_dependency_scan` CTest stays green. Without it, the classifier flags the link as `library-runtime` and fails (SC-009 of feature 001).
  2. `tools/simdjson/simdjson_purity_scan.sh` and `tools/simdjson/simdjson_nm_proof.sh` are added, modeled on `tools/hwloc/hwloc_purity_scan.sh` and `hwloc_nm_proof.sh`, and registered in `test/CMakeLists.txt` as `simdjson_purity_scan` and `simdjson_nm_proof`. The audit substring is `simdjson` (case-insensitive): it matches mangled vendored symbols (`_ZN8simdjson...`), the discovery-call pattern `find_package( *simdjson` / `pkg_check_modules( *simdjson`, and `include/` cleanliness, so presence proofs (SC-009) and absence audits (SC-002 through SC-005) read one pattern.
  3. `.github/workflows/ci.yml`: every checkout already carries `submodules: true`, so the new submodule is fetched by the existing jobs unchanged; the `test` job gains install-tree and package-config simdjson audits beside the hwloc ones (lines 121-124); `shared-audit` gains an `nm -D --defined-only ... | grep -i simdjson` step (line 173); `downstream-consumer` gains a `grep -i simdjson` over its logs (line 202). No new host toolchain: simdjson needs no autoconf/automake/libtool/patch, and the existing jobs already install those for hwloc.
- **Rationale**: FR-008, FR-009, FR-016, FR-017. The infrastructure specs/003 built (submodule checkouts, shared-audit, downstream-consumer, the purity/nm script pair) is exactly the surface this feature extends; reusing it keeps each audit's failure diagnosis readable and adds no new job shape. FR-009's static-analysis exemptions are structural except where the wrapper TU pulls vendored headers (R-008) and where the dependency classifier must know the new private link. `.codespellrc` already skips `*/external` (added by specs/003, line 8), so the vendored tree is spell-exempt with no edit: a difference from feature 003, which added that skip.
- **Alternatives considered**:
  - *Fold every simdjson audit into a new dedicated job*: rejected: the audits land where install, shared-build, and consumer runs already happen; separate jobs add no diagnosis value (specs/003 R-012 reasoning).
  - *Add `simdjson` to the `.codespellrc` skip explicitly*: rejected as redundant: `*/external` already covers `external/simdjson`.
  - *Skip the dependency_scan classifier edit*: rejected: the scan fails a `target_link_libraries(... speedgun-ng_speedgun-ng ... simdjson...)` line as `library-runtime`; the vendored-private classification is the documented-justification path the existing hwloc entry uses.
