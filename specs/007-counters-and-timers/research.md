# Research: Standalone Counters Library

**Feature**: `007-counters-and-timers` | **Date**: 2026-09-25 | **Plan**: [plan.md](plan.md)

Authoritative design record: [sg_counters.md](sg_counters.md) (closed journal, A1–A29) and [spec.md](spec.md) (clarifications session 2026-09-25 binding). Where the journal's older axis text conflicts with a clarification or an FR, the spec wins; each such point is decided below.

## R-001 Public surface: namespace, headers, export

**Decision**: Namespace `sg::counters` for the whole feature. Flat header set directly under `include/speedgun-ng/`: umbrella `counters.hpp` plus component headers `counters_core.hpp` (dimensions, units, availability, catalog entry, `metric_result`, recoverable-error type), `counters_provider.hpp` (provider contract), `counters_system.hpp` (system, objects, selection, resolution), `counters_measurement.hpp` (expressions, plan, recorder, folds, scope sugar), `counters_fake.hpp` (the shipped fake provider's control surface, R-009), `counters_clock.hpp` (the shipped clock provider's leaves, R-007), `counters_push.hpp` (the shipped push counter handle, R-008), `counters_pmu.hpp` (the shipped hardware event provider, R-010). Exported symbols carry `SPEEDGUN_NG_EXPORT` from the generated export header.

**Rationale**: The established house namespace root is `sg::` with a per-feature sub-namespace (`sg::dbc` in `include/speedgun-ng/dbc.hpp`); the string `speedgun::ng` appears nowhere in the tree. `include/speedgun-ng/` is flat today (two headers, zero subdirectories); a flat `counters_*.hpp` family preserves that shape and keeps the dbc-gate doxygen pass (which walks `include/speedgun-ng`) unchanged. The journal skeleton spells the namespace bare `sg`; that sketch predates the convention check, and constitution I (P1: established repository patterns) governs. The umbrella header is the documented single include for users.

**Alternatives considered**: bare `sg::` for counters names (pollutes the root namespace shared with `sg::dbc`, and the journal sketch carries no authority over P1 conventions); `speedgun::ng::counters` (invents a root the repo never used); per-feature subdirectories under `include/speedgun-ng/` (no precedent; the nine headers fit flat).

## R-002 Error model: three tiers mapped onto standard and DBC machinery

**Decision**: Tier 1 (compile-time): dimension violations carried by the expression type; the `metric_result` struct shape is structural. Tier 2 (recoverable): every resolution, registration, and construction-input failure returns `std::expected<T, resolution_error>`; `resolution_error` carries a message plus a suggestions list built from catalog names and descriptions. Tier 3 (contract): `SG_REQUIRE` / `SG_REQUIRE_ALWAYS` / `SG_INVARIANT` from `include/speedgun-ng/dbc.hpp`, per spec FR-046 and the dbc facility vocabulary.

**Rationale**: `std::expected` is C++23 (P0, standard-first), forces call-site handling without an exception convention the repo has never adopted, and keeps error data (did-you-mean lists) in a typed payload. The spec assigns exactly one mechanism per failure class (FR-046); mapping each class onto a different, established mechanism removes all judgment calls from the read path: tier-3 checks compile out in release except the `SG_REQUIRE_ALWAYS` bounds check FR-027 mandates. Implementation-phase check: toolchains predating `std::expected` would force a minimal in-house expected in a detail header; the dev preset compilers must be verified at implement time (task bookkeeping: the type interface is fixed either way, and the design has no fork there).

**Alternatives considered**: exceptions for tier 2 (the repo ships no exception-based public API, and `consumer-release` semantics favor value-carrying failure); error codes alone (cannot carry suggestion lists without out-params); a bespoke `sg::result` (reinvents `std::expected`, violates the standard-first rule at P3).

## R-003 Dimension algebra representation

**Decision**: `template <int T, int C> struct dim` (time exponent, events exponent), exactly the journal A10 tag `time^T x events^C`. Expressions are `template <dim D> class expression`; `operator+`/`operator-` `static_assert` identical tags; `operator/` instantiates the quotient tag by subtracting exponents (constexpr arithmetic on the tag); scalar multiply is unrestricted. The runtime leaf carries no dimension: resolved counters hold a leaf-slot index, and every dimension lives in the type, erased before the point buffer (FR-016). The catalog unit-to-dimension map is a closed `switch` returning `std::expected`; an unrecognized unit is a tier-2 error naming the unit (FR-017).

**Rationale**: A 2-int tag makes the whole algebra a constexpr type computation: `bytes / monotonic` yields `dim<−1, 1>` at compile time and the read path touches only `uint64` columns and doubles. The closed switch is the single review surface for accepted units, and it makes "guessed dimension" unrepresentable. `events^1 + events^1` still compiles; the accepted limitation (A10) is documented at the operator.

**Alternatives considered**: per-event-kind unit groups (A10 option b: template hostility, cast-escape erosion, rejected by owner); plain `double` with no algebra (A10 option c: nonsense ships); runtime unit checking (violates FR-015's compile-error mandate for `bytes + monotonic`).

## R-004 Provider contract shape and read-path dispatch

**Decision**: A C++20 `provider` concept defines what an out-of-tree provider implements: enumerate (objects with entries: name, description, unit, availability) and open (a window reader yielding one cumulative point per managed leaf per sampling action, with the unit, description, availability, and multiplex pair reachable from the catalog and the plan after measurement). Registration into the system is through a type-erased stable base class (virtual calls are confined to setup: enumerate, open, plan-compile). Plan compilation flattens everything the recorder ever touches: one leaf slot per managed leaf, and per PMU group one leader read action; `sample()` iterates a flat array of tiny read descriptors (memcpy-style loads, one group `read()` per PMU leader, push plain loads, fast-mode in-instruction reads) carrying no expression tree and no name lookup, and enters each window through the direct-call thunk the window constructor installed, so the five shipped windows reach `read_points` with no vtable lookup (FR-022, FR-026). A provider window installing no thunk keeps the default thunk, which routes to `read_points` through the vtable at one lookup per sampling action, and the giraffe example runs on that path.

**Rationale**: The core vocabulary stays provider-free (FR-010) because the concept names catalog/point/metadata only. Setup is the slow region (FR-021, A19): erasure there costs nothing. The thunk seam is what the no-dispatch read path rests on: flattening at compile time is what makes a syscall-mode `sample()` "one group read per PMU leader plus vDSO reads plus plain loads within one action" and a fast-mode `sample()` a short in-instruction sequence, and the documented fallback costs a window that installs no thunk one vtable lookup per sampling action, which is the price of implementing the window contract alone.

**Alternatives considered**: virtual `read_leaf()` per leaf per sample (a vtable lookup per leaf per sample, where the thunk seam FR-022 keeps spends one per sampling action on the fallback path alone); template-only system holding provider types (breaks runtime registration and out-of-tree providers compiled separately; the giraffe links against the built library, and relinking the library would forfeit that proof); `std::function` per leaf (allocation and indirection on the read path).

## R-005 Plan, arena, recorder layout

**Decision**: `compile(system, expressions...)` produces a `plan`: leaf slot table (slot, provider read descriptor, point-column offset), PMU group layout over the one sampling target the plan bound (FR-024), per-leaf achieved read mode, a fold program per expression (per composite: sequence of column references with algebraic exponents and ops), and the arena geometry. The arena allocates, at each `recorder` call, one `uint64` array of `capacity` slots per leaf column (column-major SoA), plus scratch for group reads. `recorder` is a trivially copyable value handle: buffer pointer, head index, policy state; multiple recorders over one plan take independent arena buffers sharing the compiled layout (FR-029). The scope spelling (`start`/`finish`/`metric`) is sugar over a two-point recorder, with its two columns living in the scope object itself (no arena round trip needed; semantics identical, FR-030).

**Rationale**: Column-major per-leaf arrays make folds plain vectorizable subtractions over contiguous ranges (A25), and `sample()` writes exactly one `uint64` per column per call. Value-handle semantics kill lifetime puzzles in gbench-style loops (A27) where the recorder is created in the untimed setup region and captured by the loop. Fold-time modularity follows: folds read only recorded columns, never providers (FR-021).

**Alternatives considered**: row-major per-sample columns (worse fold vectorization, identical sample cost); per-recorder heap allocation (breaks "all construction in the untimed region is plan-arena" and multi-recorder sharing of layout); reference-semantic recorder (A27 rejected: lifetime puzzle in loop bodies).

## R-006 Overflow policy types and the recorder factory

**Decision**: Two policy models, `hard_stop` (default) and `ring`, passed as constexpr tag values through one factory: `plan.recorder(capacity)` and `plan.recorder(1024, sg::counters::ring)`; CTAD selects the instantiation; no visible template arguments at call sites (FR-025). `hard_stop`: bounds check is `SG_REQUIRE_ALWAYS` (enforced in every configuration including release: memory safety is never semantic-gated). `ring`: power-of-two capacity enforced at construction as a tier-2 `std::expected` failure; index update `idx & (cap - 1)` branchless; a one-shot promotion branch flips wrapped state once, then the loop is branch-free; wrapped flag and dropped count recorded; every fold over a wrapped ring consults `dropped` inside the fold layer (FR-028).

**Rationale**: A runtime mode flag is one branch per `sample()` forever; a type is zero branches, chosen where slow is allowed (A26). `SG_REQUIRE_ALWAYS` for bounds matches the spec edge case "release included: memory safety is never semantic-gated", and costs one perfectly predicted branch beside the clock read. A non-power-of-two ring capacity is a construction input failure: the caller can recover by choosing another capacity, so it is tier 2, and FR-046's tier-3 list names only overrun, misuse, decrements, bad ranges.

**Alternatives considered**: runtime flag (branch per sample, rejected A26); grow-on-demand (allocation on the read path is the one inviolable rule); tier-3 abort on non-power-of-two capacity (recoverable input deserves recovery; abort reserved for developer misuse where no legal recovery exists mid-call).

## R-007 Clock provider

**Decision**: Leaves on the machine object: `monotonic` (`clock_gettime(CLOCK_MONOTONIC)`), `thread_cpu` (`CLOCK_THREAD_CPUTIME_ID`), `process_cpu` (`CLOCK_PROCESS_CPUTIME_ID`), all dimension `time^1`, mode `syscall` (vDSO regime). Plus `tsc` on x86-64 where calibration succeeds: `__rdtsc` (or `rdtscp` variant where spectre posture requires), frequency calibrated at provider construction, the last boundary at which the leaf can be seeded because the catalog freezes at the open boundary, from `tsc_khz` sysfs cross-checked against CPUID frequency invariance data; the achieved mode (`fast_tsc`) and the calibration provenance (frequency source, scaled-TSC flag) are catalog fields (FR-033, FR-034). Platforms without a usable TSC simply omit the leaf: a catalog fact, no API difference (FR-042).

**Rationale**: Three kernel clocks are two `clock_gettime` id constants and one clock id each; zero privileges (SC-002). The TSC leaf exists because the hot path needs a tens-of-cycles time read (A29 reversal of the original TSC exclusion); calibrating from sysfs plus a CPUID invariance check is the minimum, and the scaled flag reports the lie the hardware tells on scaled-TSC machines. Full wall-clock conversion machinery stays out of scope per spec Assumptions.

**Alternatives considered**: `std::chrono::steady_clock` as the only clock (hides clock-id choice, cannot expose thread/process CPU times as leaves); TSC uncalibrated (a wrong frequency silently scales every rate metric; the calibration is the leaf's contract); `rdpid`-based core pinning checks per read (out of scope; per-thread binding covers the correctness need).

## R-008 Push provider: thread confinement, plain non-atomic

**Decision**: `add(n)` is a plain `uint64 += n` and the sample read is a plain load; no atomic RMW on any path. Confinement: the counter records the creating thread; `add()` and sampling from another thread are tier-3 violations enforced with semantic-gated `SG_REQUIRE` (compiled out in release, live in dev/CI). A decrement between recorded points is a tier-3 violation detected at fold time (FR-035). This supersedes the journal's older "relaxed atomic" wording (A4/A22): the spec clarification session 2026-09-25 decided single-thread confinement, and the FR governs.

**Rationale**: Confinement is the contract; within it, atomics buy nothing and cost a lock-prefixed instruction per increment. The thread-id check reads the current thread's identity per call and compares it against the cached one the counter recorded at creation, because caching the answer would cache it for the thread that cached it; the check exists solely in dev/CI builds, and release builds carry zero overhead on a hot-path increment (P0 critical-path designation, documented). Fold-time decrement detection covers the "user moved the counter between samples" case without hot-path cost.

**Alternatives considered**: relaxed atomic add (contradicts FR-035 after the clarification; also invites cross-thread use the contract forbids); per-thread shards with fold-time summation (sharding policy belongs to the future threading spec, spec clarification 3); always-on thread check (a branch per increment in release, and memory safety is not at stake: confinement violation is developer misuse).

## R-009 Fake provider

**Decision**: Shipped in the public headers plus library sources (`counters_fake.hpp` re-exported via the umbrella; provider class `fake_provider`). Construction takes hand-driven scripts: per leaf, either an explicit point sequence or a per-sample delta generator (seeded, deterministic). The API is test-facing: scripts accept crafted values including a sequence that walks one leaf across `2^64` to exercise the wrap. It registers arbitrary object trees (two packages, multi-core shapes) on demand, so US3/US5 tests never need privileged hardware (FR-036).

**Rationale**: The fake is the provider contract's conformance spine (A7): every catalog, algebra, recorder, fold, and provenance assertion in the suite runs against hand-driven exact numbers, zero sleeps, zero privileges (SC-002, SC-006). Shipping it (FR-036, library target) makes downstream test suites able to use the same spine; keeping its control surface out of the core (it is an ordinary provider) proves FR-012 at every test run.

**Alternatives considered**: test-private fake under `test/` (FR-036 mandates the library ships it); a fake clock substituted into the clock provider (fails the abstraction test: the fake must be an ordinary provider).

## R-010 linux_pmu provider: tables, merge, encoding, availability

**Decision**: Open sequence: read CPUID (vendor/family/model) → match through the vendored `mapfile.csv` (regex per line, first match selects the architecture table directory) → parse that directory's JSON once, lazily, with the vendored simdjson (private: `source/counters/linux_pmu/` TUs are the only includers) → enumerate sysfs `/sys/bus/event_source/devices/*` (PMU type ids, `format/` bit layouts, `events/` aliases) and merge: kernel-discovered aliases win conflicts (FR-037) → probe availability per entry by `perf_event_open` test-open plus `perf_event_paranoid` read → report `countable` / `permission_blocked` / `not_encodable` / `absent` (FR-006, FR-039). Event encoding composes JSON semantic `EventCode`/`UMask` with sysfs `format/<field>` bit positions; a missing format field marks the entry `not_encodable`, encoding never half-attempted (FR-037). Plan layout binds the one sampling target the plan took and hands that value to every provider's `open()`, so a target or clock-identity mismatch across group members is unrepresentable (FR-024); the construction errors a single target still fails on are a leaf the catalog reports as not `countable` and a window the provider refuses to open. Syscall-mode `sample()` performs one group `read()` per PMU leader (`PERF_FORMAT_GROUP`, values plus `time_enabled`/`time_running` into scratch) per sampling action (FR-026); enabled and running are ordinary cumulative leaves appended to every group's leaf set (FR-041). `MetricExpr` rows are carried as catalog data only, ingested by no 007 code.

**Rationale**: JSON carries semantics, sysfs carries this kernel's bit layout, and composing them survives table/kernel skew (jevents' proven decoupling, journal A17). Lazy parse of one architecture directory keeps system-open cost noise-level with simdjson already vendored privately (004 landed exactly this seam). Probing is the only truth of schedulability and permission (journal A16): encoding-known and countable-now are distinct predicates. The provider's availability probe maps `EINVAL`, `EOPNOTSUPP`, and `ENOENT` to `not_encodable` and reports `permission_blocked` from its default arm, which covers `EACCES` together with every other refusal, and the re-verification at `perf_event_paranoid` 2 recorded 358 hardware entries probing `countable` with 0 `permission_blocked`, so the suite stays green at the level CI runs unprivileged (SC-002, `docs/pages/counters-overhead.md:314-334`); the level where the kernel refuses the availability probe's test-opens with a permission error is 3 or above, which the same record states.

**Alternatives considered**: distro `/usr/share/perf-core/vendor_events` as primary source (distro-dependent thinness, A17 rejection); hand-coded event constants (the catalog-as-data design forbids it); eager full-tree parse (wasted work: only the CPUID-matched directory is ever relevant); `perf` CLI subprocess (a runtime dependency and unparsable drift, forbidden by the zero-dependency constraint).

## R-011 Fast mode: mmap-page rdpmc protocol

**Decision**: `fast_rdpmc` leaf setup: `perf_event_open` per-thread context (group member with leader fd), single-page read-only `mmap`; reads follow the mapped-page protocol: snapshot `lock` (seqcount), `rmb`, read `index`/`offset`/`cap_user_rdpmc`, `index == 0` or capability false means taking the recorded fallback path (the read descriptor states it), `_rdpmc(index - 1)` (kernel indices are 1-based), `rmb`, retry while `lock` changed; result `(raw + offset)` masked to the width `pmc_width` publishes on that page. Support is probed, never assumed: mmap-page mechanism availability and counter index validity, both read from the event page the kernel maps, reached through a standard `static_cast` of the kernel's own `perf_event_mmap_page` at the offsets the running kernel's UAPI header fixes; fast binding is per-thread same-thread context (FR-031, FR-040). The protocol follows `jevents/rdpmc.{c,h}` from andikleen/pmu-tools (BSD-style permit with attribution); the implementation is C++ in our tree with an attribution comment citing the reference (no file copied). Staleness while off-CPU stays disclosed because `time_enabled`/`time_running` remain ordinary leaves and every fold computes the ratio (FR-041). The fast-mode benchmark lands only where its probe passes; elsewhere it skips with the failure named (SC-004).

**Rationale**: RDPMC returns exactly a point (A25): the fastest mechanism fits the ontology unchanged. Every gate (capability, index, counter width `pmc_width`) is host state the probe reads from the event page the kernel maps for it, reached through a standard `static_cast` of the kernel's own `perf_event_mmap_page`; hardcoding kernel version folklore is explicitly distrusted by the spec assumptions. Attribution is the license's only condition and one comment carries it.

**Alternatives considered**: bare `rdpmc` without the seqcount protocol (torn reads and stale-index UB; the protocol is the mechanism); `perf_event_mmap` per-CPU ring (orders of magnitude heavier, wrong mechanism); assuming the host grants a user counter read, which settles nothing about the `pmc_width` the mapped `perf_event_mmap_page` publishes or the standard `static_cast` that reads that page at the kernel's own offsets (the probe decides); copying the jevents C file verbatim (attribution would cover it, but the C++ implementation is smaller than the comment justifying an unmanaged C file).

## R-012 Vendored pmu-events tree and the version gate

**Decision**: `external/pmu-events/` holds a byte-exact path snapshot of the kernel's `tools/perf/pmu-events` (x86 architecture table directories plus `mapfile.csv`) committed as ordinary files. A submodule fits badly here: the source is a path inside the kernel tree, and a kernel submodule would drag 140 MB for a few MB of JSON. A `RECORD` manifest file carries the upstream ref, fetch date, URL, per-file sha256, and the explicit exclusion list. The version gate follows the yaml-cpp precedent (configure-time tripwire, no git metadata consulted): a bracket in the root `CMakeLists.txt` reads `RECORD`, compares the recorded ref against the gate constant held in the CMake file, and fails configuration on drift. The `--check` tool (R-013) verifies hashes and gate in CI. Licensing: the data is dual MIT/GPL-2.0-or-later; the BSD-3-compatibility confirmation for data-only redistribution is an explicit early implementation task with a documented fallback (sysfs-discovered catalog, same interface, spec Assumptions).

**Rationale**: The house gate pattern is a recorded-constant tripwire that fails the build until re-pinned (README re-pinning sections for hwloc/simdjson/hdrhistogram/zlib/yaml-cpp; journal A15 notes the fit). Byte-exact vendoring keeps the review diff the upstream diff (A18 decision). A configure-time check is the correct rung because JSON data exposes no version macro to `static_assert` against; yaml-cpp 0.9.0 established exactly that precedent.

**Alternatives considered**: git submodule of the full kernel (absurd weight for a path snapshot); sparse checkout machinery at build time (network at build time is forbidden; reproducibility rule); normalizing the JSON to a canonical form (destroys upstream diffability, A18 rejected); compile-time gate TU (nothing to assert against: no version macro in JSON files).

## R-013 Upgrade utility `tools/pmu_events/update_pmu_events.py`

**Decision**: One python3 script, two modes. `--to <kernel-ref>`: fetch the `tools/perf/pmu-events` path archive from kernel.org cgit (documented GitHub mirror fallback), strip to the in-scope x86 table directories plus `mapfile.csv` recording an explicit exclusion list, validate every file parses (json) and passes schema sanity (`EventName`/`EventCode` present on event entries, mapfile regexes compile), only then replace the tree byte-exact, rewrite `RECORD` (ref, date, URL, per-file sha256, exclusions), bump the gate constant (the CMake bracket's constant is the single bump point), and print the per-architecture old-to-new event-count digest. Failure at any validation point leaves the tree untouched (replace-last, into a staging directory). `--check`: verify tree hashes against `RECORD` and the gate constant against the recorded ref; drift exits 1 naming the file; no network access ever. Fixtures: tiny synthetic table trees wired into CTest (the `prose_gate_fixtures` pattern), passing and intentionally drifted.

**Rationale**: FR-044 and FR-045 specify the behavior; the house precedent for a python3 tool with `--check`, CI wiring, and ctest fixtures is `tools/prose/` (constitution-adjacent practice). Replace-last semantics make a partial fetch incapable of corrupting the vendored tree (US8 scenario 4). CI wiring is one step in the existing test job.

**Alternatives considered**: a CMake script (YAML/JSON tar handling in CMake is suffering, and the house tool language is python3); a shell script (validation logic needs json parsing; python is stdlib-sufficient); running `--to` in CI (fetch mode is developer-triggered by spec; CI never fetches, FR-045).

## R-014 Per-plan overhead calibration and benchmark delivery

**Decision**: After plan finalization, the plan exposes a calibration operation: repeatedly run the plan's `sample()` over an empty workload and report the read-path overhead as a distribution (min / median / max, ns), stored on the plan so every fold window can state its endpoint cost (FR-032, cadence contract). Delivery: a `counters_overhead` executable built like a test, registered in CTest with probe-gated skips (`SKIP_RETURN_CODE 2` for hosts where fast mode is unavailable; the skip reason prints). The reference-host distribution is recorded in `docs/pages/counters-overhead.md` following `docs/pages/dbc-overhead.md`. The zero-allocation proof (SC-005) is separate and always-on: a test TU installs counting global `operator new`/`delete` and asserts `sample()` runs with a zero allocation count.

**Rationale**: VII demands critical-path performance cases with distributions; the open deferral (baseline infrastructure absent) means this feature ships the measurement artifacts and their publication path, while the regression-gate wiring waits for the baseline spec. `SKIP_RETURN_CODE` is CTest's native skip mechanism (fast-mode acceptance is explicitly probe-gated by US7 scenario 6). Allocation counting by interposition needs no new dependency.

**Alternatives considered**: gbench-style third-party benchmark harness (FR-049 forbids benchmarking-framework code anywhere in 007; also a new dependency); asserting cycle budgets as hard test failures (host-dependent; the spec's fast-mode acceptance is probe-gated by design); malloc interposition via `LD_PRELOAD` (fragile in CI containers; in-process counting operators are deterministic).

## R-015 Threading contract enforcement points

**Decision**: `system` and catalogs are populated before open and immutable after; open is the constructor-side boundary, so concurrent catalog reads are safe by construction (FR-009). Plans bind targeting (thread or cpu) at plan open; plans and recorders are per-thread values with tier-3 `SG_REQUIRE` checks on recorder use from a non-binding thread where the check is cheap (a fresh `thread::id` query compared against the cached `bound_thread`, beside the always-enforced bounds check; caching the current thread's identity would cache the answer for the thread that cached it). Push counters confine to the creating thread (R-008). Fast-mode contexts bind per-thread same-thread (FR-040). Folds consume one recorder's columns only (FR-047).

**Rationale**: The kernel rule (per-thread perf contexts) is underneath the API rule (journal A28 threading contract); checking binding where a check already exists (bounds check site) keeps the hot-path cost at one predictable compare in dev/CI. Immutability after open removes the catalog race question entirely: no lock is needed anywhere.

**Alternatives considered**: lock-protected catalogs (cost for a state that never needs it after open); global plans (spec FR-031 makes multiple plans first-class and forbids the single-instance assumption); runtime cross-thread detection for push counters in release (developer misuse with no memory-safety consequence; dev/CI is the enforcement tier FR-046 chose).
