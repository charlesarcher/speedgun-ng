  So the lane's measured shape is `attr.type = 0` (PERF_TYPE_HARDWARE) with
  `attr.config = 4` (PERF_COUNT_HW_BRANCH_INSTRUCTIONS): the generic request,
  which the kernel translates to the part's own encoding inside perf_event_open.

specs/041-counter-probe/tools/group_probe.c (184 lines): the tool that recorded
  those figures. perf_open() sets `attr.type = PERF_TYPE_HARDWARE` and
  `attr.config = config` (argv[1], default 4), exclude_kernel 1, exclude_hv 1,
  disabled 1, pinned 0, read_format TIME_ENABLED|TIME_RUNNING; the open binds
  pid 0, cpu -1, group_fd = the first descriptor. Table 1 sweeps k = 1..max_k,
  Table 2 sweeps to 96 for a refusal, Table 3 is the linear search and its cost.

The shipped search: source/counters/linux_pmu/group_probe.cpp
  fillProbeAttr(): `attr.type = options.pmuType`, `attr.config =
  options.eventConfig`, exclude_kernel 1, exclude_hv 1, disabled 1, pinned 0,
  read_format TIME_ENABLED|TIME_RUNNING; pid 0, cpu -1, group leader = first
  descriptor. Same attribute shape as the tool except that type and config are
  the device's own pair. Two more differences, recorded because they are real:
  the shipped open passes PERF_FLAG_FD_CLOEXEC where the tool passes 0, and the
  shipped enable/disable is one ioctl on the leader with PERF_IOC_FLAG_GROUP
  where the tool ioctls every descriptor of the group.
  `options.pmuType` is the device's own type number: provider.cpp:324-334
  slurps `<device>/type` into `device.type`, and provider.cpp:671 puts it in
  `attr.type`. `options.eventConfig` is composed by pmuComposeConfig() in
  source/counters/linux_pmu/encode.cpp from `<device>/events/<name>` against
  `<device>/format/*`.

Prior artifacts this replaces: requirement-1-zen5-paranoid2.txt answers 6 at
  0.070 ms, requirement-1-zen5-paranoid-minus1.txt answers 6 at 0.073 ms. Both
  ran the measured shape. spec.md F-5, D-6, SC-009 and the budget note publish

## Step 2: the device PMU pair, and the config word composed by hand

/sys/bus/event_source/devices/cpu/type                  -> 4
/sys/bus/event_source/devices/cpu/events/*              -> 8 events:
    branch-instructions: event=0xc2
    cpu-cycles:          event=0x76
    instructions:        event=0xc0
    ref-cycles:          event=0x120,umask=0x01
    (branch_miss and bus-cycles are not published on this part)
/sys/bus/event_source/devices/cpu/format/*
    cmask:  config:24-31
    edge:   config:18
    event:  config:0-7,32-35
    inv:    config:23
    umask:  config:8-15

The searched event is branch-instructions, whose words name one field:
`event = 0xc2`. Composition, per pmuComposeConfig() (a field published as
several bit ranges splits its value across them in file order, and the parts
of different fields are OR-ed into the same config word):

    field "event", value 0xc2
      range 1  config:0-7    width 8, capacity 0xff
               chunk = (0xc2 >>  0) & 0xff = 0xc2 -> 0xc2 <<  0 = 0x00000000000000C2
      range 2  config:32-35  width 4, capacity 0x0f
               chunk = (0xc2 >>  8) & 0x0f = 0x00 -> 0x00 << 32 = 0x0000000000000000
      residual (0xc2 >> 12) = 0, so the value fits its ranges.

    config word 0 = 0x00000000000000C2 | 0x0000000000000000 = 0x00000000000000C2 = 194

    shipped pair:  attr.type = 4,  attr.config = 0xc2 (194)

Worked two-field case, to show the OR of parts (not the searched event; it is
the shape ref-cycles takes on the same device, `event=0x120,umask=0x01`):

    field "event", value 0x120
      config:0-7   chunk = 0x120 & 0xff = 0x20 -> 0x20 <<  0 = 0x0000000000000020
      config:32-35 chunk = (0x120 >> 8) & 0xf = 0x01 -> 0x01 << 32 = 0x0000000100000000
    field "umask", value 0x01
      config:8-15  chunk = 0x01 & 0xff = 0x01 -> 0x01 <<  8 = 0x0000000000000100
    config word 0 = 0x20 | 0x0000000100000000 | 0x100 = 0x0000000100000120

Note on the number 4: this kernel happens to assign the dynamic perf type 4 to
the `cpu` device, and 4 is also the constant PERF_TYPE_RAW. The shipped shape
reads 4 from the device's own `type` file, not from perf_type_id; the two 4s are
a coincidence on this host, not the same fact. The type numbers of the other
devices on this host (breakpoint 5, ibs_fetch 10, ibs_op 11, kprobe 8, msr 13,
amd_iommu_0 12, software 1, tracepoint 2) confirm they are per-device numbers.


## Step 3: the argv-driven probe, built

`tools/group_probe.c` copied to /tmp/041-notes/group_probe_ship.c and extended by hand:
`perf_open()` and `probe_size()` take the type beside the config, `main()` reads
`<type> <config> [maxK]` from argv (usage line + exit 2 when argv is short), and the
header line prints the type it was given instead of the words PERF_TYPE_HARDWARE. The
enable and the disable of every descriptor are untouched, as are the attribute's other
fields, the group shape, the three tables, and the tallies.

    cc -O2 -Wall -Wextra -Wpedantic -o group_probe_ship group_probe_ship.c     -> no warning

Two shipped-code differences this tool does not carry, recorded because they are real and
because they are the only reason to read the numbers below as a proxy:

  * the shipped open passes `PERF_FLAG_FD_CLOEXEC` (group_probe.cpp:107) where the tool
    passes 0 — a descriptor-flag difference, no scheduling effect;
  * the shipped enable and disable are one ioctl on the leader with
    `PERF_IOC_FLAG_GROUP` (group_probe.cpp:120-127) where the tool ioctls every descriptor
    of the group — both start and stop the same group, the shipped way issues two ioctls
    per size and the tool `k`.
Neither was varied here, and both shapes below ran through the same tool, so the two runs
are directly comparable to each other.

### `pinned` and `exclusive`

`/sys/bus/event_source/devices/cpu/format/` publishes five names — cmask (config:24-31),
edge (config:18), event (config:0-7,32-35), inv (config:23), umask (config:8-15) — and no
`pinned` and no `exclusive`, anywhere under the device directory. So neither can enter the
answer through the config word: there is no bit range for the composition to place them
in. They are `perf_event_attr` bitfields instead — `pinned : 1, /* must always be on PMU */`
and `exclusive : 1, /* only group on PMU */` in /usr/include/linux/perf_event.h — and the
shipped attribute leaves both clear: `fillProbeAttr()` zeroes the struct and names
`pinned = 0` on purpose (FR-013), never touching `exclusive`.

They do not matter to the answer the shipped probe gives. What they would change is the
shape of the evidence: a group the kernel cannot seat on dedicated counters answers a
refusal or an error state instead of a run shorter than its enabled window, which is the
reason FR-013 leaves `pinned` clear — the measurement depends on seeing the short run, and
both runs above show it (at k = 7 the open answers 0 and `time_running` sits below
`time_enabled`). Whether a pinned shape would answer a different k was not measured here.

## Step 5: verdict

The two shapes agree. The device's own pair (type 4, config 0xc2, what ships) and the
generic pair (type 0, config 4, what the lane measured) both answer 6 as the largest size
whose group ran its whole enabled window, both refuse no group open up to k = 96, both pay
28 opens, 28 enables, 7 reads and 28 closes for that answer, and both leave 0 descriptors
at exit. The figure SC-003 and F-4 carry — 6, equal to the decode of this part — stands.

The cost line is the one thing this run changes, and it changes it only in provenance:
0.080 ms measured in the shipped shape, 0.077 ms in the measured shape, 0.067 to 0.095 ms
across the whole series. The published 0.078 ms (F-5, D-6, SC-009, the budget note) matches
neither prior artifact — results/ holds 0.070 ms at paranoid 2 and 0.073 ms at paranoid -1,
both from the measured shape — and matches no number this file records either. Since the
two shapes agree on k, the choice of figure is not a disagreement about the host; it is a
provenance rule. The acceptance record must carry the shipped-shape reading, because the
shaped pair is what a customer's process runs: 28 opens, 28 enables, 7 reads, 28 closes and
0.080 ms at paranoid 2 on this host, with the 0.067 to 0.095 ms spread stated beside it.
Under ruling G-20 that reading is owned by the host that recorded it, and a restatement of
the single published figure in spec.md is the owner's or the writing task's call, not this
file's.
