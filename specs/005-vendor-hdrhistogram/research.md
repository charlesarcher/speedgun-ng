# Research: Vendor HdrHistogram_c as a Private, Pinned Submodule

**Feature**: 005-vendor-hdrhistogram | **Date**: 2026-09-23
**Status**: All NEEDS CLARIFICATION resolved (0 remaining).

Every fact below was verified on 2026-09-23 against the HdrHistogram_c tag `0.11.10` (lightweight tag naming commit `18c7a324383dded1451d15621cd018b0048057d0` directly, re-confirmed via `git ls-remote`) and the zlib tag `v1.3.2` (annotated tag peeling to commit `da607da739fa6047df13e66a2af6b8bec7c2a498`), plus CMake's own `FindZLIB` module, and against the speedgun-ng tree as it stands. Each decision names the requirements it settles. The simdjson import (specs/004-vendor-simdjson) is the shape precedent: both vendored libraries here are native CMake, so the `add_subdirectory` scoped-bracket machinery of 004 applies. Two things make this feature larger than 004: a companion dependency (zlib) that one vendored library requires the other to satisfy, and a vendored project (HdrHistogram_c) whose header, package-config, and pkg-config install rules are unconditional with no option to gate them. Those two facts are the research contribution here.

## Phase 0 Findings

### R-001: Ingestion mechanism = two submodules + two `add_subdirectory` scoped brackets; `ImportAutotoolsSubmodule` stays unused

- **Decision**: HdrHistogram_c enters as a git submodule at `external/hdrhistogram_c` (tag `0.11.10`, commit `18c7a324383dded1451d15621cd018b0048057d0`) and zlib at `external/zlib` (tag `v1.3.2`, commit `da607da739fa6047df13e66a2af6b8bec7c2a498`). Both are native CMake projects, both are ingested through `add_subdirectory(<dir> <binary-dir> EXCLUDE_FROM_ALL)` inside function-scoped brackets (R-011), the same mechanism specs/004 established for simdjson. The `cmake/ImportAutotoolsSubmodule.cmake` module stays unused for both.
- **Rationale**: FR-011 fixes `add_subdirectory` with `EXCLUDE_FROM_ALL` for HdrHistogram_c; the spec assumption records both trees as native CMake needing no autotools bootstrap. Verified: HdrHistogram_c's top-level `CMakeLists.txt:1` is `cmake_minimum_required`, its library targets are created by `hdr_histogram_add_library(...)` (`src/CMakeLists.txt:66,75`), no `autogen.sh`/`configure`/`Makefile.am`. zlib v1.3.2 ships an in-tree `CMakeLists.txt` (a rewrite versus 1.3.1, see R-004) whose targets are `add_library(zlib ...)`/`add_library(zlibstatic ...)` (`CMakeLists.txt:157,204`), no host autoconf/automake/libtool/patch. This is strictly less host tooling than the hwloc ingestion (specs/003 R-011). The spec assumption offered `ImportAutotoolsSubmodule` as an alternative for zlib because 1.3.x historically shipped a `configure`; the v1.3.2 CMake path makes that unnecessary, so the plan records `add_subdirectory` for both and introduces no new host build tool.
- **Alternatives considered**:
  - *FetchContent / registry distribution*: rejected by the spec (vendoring or nothing, Scope boundaries).
  - *`ImportAutotoolsSubmodule` for zlib*: rejected: its job is to run `autogen.sh` and an out-of-tree `configure` in a copied autotools tree. zlib v1.3.2 has a first-class CMake build that also generates `zconf.h` into the binary directory (R-010), so `add_subdirectory` keeps the submodule pristine (SC-007) with no copy step. Reusing the autotools module would add machinery with no job (constitution X.2).
  - *One combined bracket for both trees*: rejected: the two trees have different option sets and a hard ordering constraint (zlib must be configured and its redirect published before HdrHistogram_c runs `find_package(ZLIB)`, R-008). Two named brackets make that order explicit.

### R-002: HdrHistogram_c version assertion = `static_assert` on the `HDR_HISTOGRAM_VERSION` string macro

- **Decision**: The wrapper TU asserts `static_assert(std::string_view{HDR_HISTOGRAM_VERSION} == "0.11.10", "...expected HdrHistogram_c 0.11.10...")`, after `#include <hdr/hdr_histogram.h>` (which pulls `hdr/hdr_histogram_version.h`).
- **Rationale**: FR-003 demands exactly 0.11.10 with a readable diagnostic. The only version identifier HdrHistogram_c 0.11.10 exposes is the single string macro `#define HDR_HISTOGRAM_VERSION "0.11.10"` (`include/hdr/hdr_histogram_version.h:10`). Verified negative findings: there is no `HDR_HISTOGRAM_VERSION_MAJOR`/`_MINOR`/`_PATCH`, no `HDR_HISTOGRAM_VERSION_STRING`, and no `hdr_histogram_version()` function anywhere in the tree. `#if HDR_HISTOGRAM_VERSION == "..."` is invalid (the preprocessor cannot compare strings), and there are no numeric components to compare. A `constexpr` `std::string_view` equality is the compile-time gate; on failure the compiler prints the message text (naming 0.11.10) plus the evaluated operands, so the diagnostic identifies both the expected version and the mismatch (FR-003). The `configure_file(hdr/hdr_histogram_version.h ...)` at `include/CMakeLists.txt:1` is a verbatim copy: the source header carries no `@...@` token, its value is the literal `0.11.10`, and the build-interface include dir is the source `include/` (`src/CMakeLists.txt:48`), so the wrapper sees the literal either way.
- **Alternatives considered**:
  - *Numeric triple (the hwloc/simdjson shape, specs/003 R-002, 004 R-002)*: rejected: those libraries expose MAJOR/MINOR/REVISION constants; HdrHistogram_c does not. The string comparison is the only compile-time reading.
  - *Regex-parse the macro at configure time and pass a `-D` to the compiler*: rejected: adds a configure step and a second source of truth; the macro is already a clean literal `0.11.10` with no release-candidate suffix (contrast hwloc's `2.14.0rc2-git`), so a direct string compare at the use site is the minimum.

### R-003: zlib version assertion = `static_assert` on `ZLIB_VERSION` and `ZLIB_VERNUM`

- **Decision**: The zlib wrapper TU asserts `static_assert(std::string_view{ZLIB_VERSION} == "1.3.2", "...")` and `static_assert(ZLIB_VERNUM == 0x1320u, "...")`, after `#include <zlib.h>`.
- **Rationale**: FR-003 requires the second compile-time assertion to verify zlib 1.3.2 through `ZLIB_VERSION`. `zlib.h` defines `#define ZLIB_VERSION "1.3.2"`, `#define ZLIB_VERNUM 0x1320`, and `ZLIB_VER_MAJOR 1 / ZLIB_VER_MINOR 3 / ZLIB_VER_REVISION 2 / ZLIB_VER_SUBREVISION 0`. Verified negative finding: there is no `ZLIB_VER_PATCH` macro; the patch level is `ZLIB_VER_REVISION`. The string is the required check; the hex `ZLIB_VERNUM` integer is added because `#if`/`static_assert` read it directly and it rejects a patch drift with no ambiguity. The assertion compiles against the real `zlib.h` from the vendored include interface (R-009).
- **Alternatives considered**:
  - *Assert the `ZLIB_VER_*` integer quadruple*: admissible, kept secondary. `ZLIB_VERSION` is the macro the requirement names; the quadruple duplicates it. The pair (`ZLIB_VERSION`, `ZLIB_VERNUM`) is the concise primary.
  - *`#if ZLIB_VERNUM == 0x1320` alone*: rejected as the sole gate: FR-003 names `ZLIB_VERSION` explicitly, and the string form reads identically to the HdrHistogram_c assertion, keeping the two gate files uniform.

### R-004: Build options = force each library static and library-only; the logging component stays enabled

- **Decision**:
  - HdrHistogram_c bracket: `HDR_HISTOGRAM_BUILD_SHARED OFF`, `HDR_HISTOGRAM_BUILD_STATIC ON`, `HDR_HISTOGRAM_INSTALL_SHARED OFF`, `HDR_HISTOGRAM_INSTALL_STATIC OFF`, `HDR_HISTOGRAM_BUILD_PROGRAMS OFF`, `BUILD_SHARED_LIBS OFF` (belt for R-007), and `HDR_LOG_REQUIRED` left at its default `ON`.
  - zlib bracket: `ZLIB_BUILD_SHARED OFF`, `ZLIB_BUILD_STATIC ON`, `ZLIB_INSTALL OFF`, `ZLIB_BUILD_TESTING OFF`, `ZLIB_PREFIX ON` (R-009), `BUILD_SHARED_LIBS OFF`, `CMAKE_POSITION_INDEPENDENT_CODE ON`.
- **Rationale**: FR-011 and Clarifications 2026-09-23 (Fixed decisions 6 and 7). HdrHistogram_c option defaults are all `ON`: shared build/install (`src/CMakeLists.txt:63,64`), static build/install (`src/CMakeLists.txt:72,73`), programs (`CMakeLists.txt:72`). `HDR_HISTOGRAM_BUILD_PROGRAMS OFF` removes the `add_subdirectory(test)` and `add_subdirectory(examples)` pulls in one stroke (`CMakeLists.txt:73-81`), so no test/example target exists to build or install. Turning both install options `OFF` also disables the gated library-target install (`src/CMakeLists.txt:54`) and the gated `install(EXPORT ...)` (`CMakeLists.txt:91-92`). The logging component stays `ON`: `HDR_LOG_REQUIRED` defaults to `ON` and is deliberately not set to the string `DISABLED`; disabling a dependency's capability to dodge its zlib requirement is prohibited (Clarifications). With logging on, `src/CMakeLists.txt` compiles `hdr_histogram_log.c` and links `ZLIB::ZLIB` (R-008), so the vendored logging translation units build against the vendored zlib. zlib v1.3.2 is the 1.3.x CMake rewrite: it introduces `ZLIB_BUILD_SHARED`/`ZLIB_BUILD_STATIC`/`ZLIB_INSTALL`/`ZLIB_BUILD_TESTING`/`ZLIB_PREFIX` options (`CMakeLists.txt:22,26,...`); `ZLIB_BUILD_TESTING OFF` removes its `add_subdirectory(test)`, `ZLIB_INSTALL OFF` removes every zlib install rule (R-010), `ZLIB_BUILD_SHARED OFF` leaves only `zlibstatic` (R-007, R-009).
- **Alternatives considered**:
  - *`HDR_LOG_REQUIRED=DISABLED`*: rejected by directive: it swaps in `hdr_histogram_log_no_op.c` to dodge zlib. The requirement is met by vendoring zlib instead.
  - *Leave `HDR_HISTOGRAM_BUILD_PROGRAMS` ON and rely on `EXCLUDE_FROM_ALL`*: rejected: `EXCLUDE_FROM_ALL` keeps targets out of the default `all` build but still registers their `install()` rules, and CTest wiring (`include(CTest)`) would add ctest entries whose targets never build, breaking `ctest` runs. Turning the switch off removes them structurally.
  - *`ZLIB_BUILD_SHARED ON` so the `ZLIB::ZLIB` alias exists*: rejected: the alias is directory-scoped and therefore invisible to the HdrHistogram_c sibling regardless (R-008), and a shared `libz` would become a runtime dependency of the shared build (SC-010). Static-only is forced; the redirect target is published in the parent scope instead.

### R-005: Link-proof symbols = `&hdr_alloc` (HdrHistogram_c) and `&zlibVersion` (zlib)

- **Decision**: The HdrHistogram_c wrapper holds `[[maybe_unused]] [[gnu::used]] constinit auto const link_proof = &hdr_alloc;`. The zlib wrapper holds `[[maybe_unused]] [[gnu::used]] constinit auto const link_proof = &zlibVersion;`.
- **Rationale**: FR-007 and FR-021 require `nm` on the built archive to show each vendored object pulled in by the wrapper's reference. `hdr_alloc` (`include/hdr/hdr_histogram.h`) is the core allocation entry point, a real out-of-line `C` symbol in `hdr_histogram_static`. `zlibVersion` is a stable out-of-line symbol in `zlibstatic`. Taking the address without calling forces an undefined reference the merged member resolves. `constinit` forbids a startup initializer, keeping each wrapper at zero runtime lines (coverage gate); `[[gnu::used]]` keeps the static alive under the coverage flag set (the identical construction `source/hwloc/hwloc_gate.cpp` and `source/simdjson/simdjson_gate.cpp` use). Under `Z_PREFIX` (R-009) the `zconf.h` rename macros redirect `zlibVersion` to `z_zlibVersion`, so the reference matches the renamed archive symbol with no special handling in the wrapper source.
- **Alternatives considered**:
  - *`&hdr_init` / `&deflate`*: rejected as less stable: `hdr_init` is a documented-but-secondary entry, and `deflate` is one of the names SC-011 audits for absence from exports, so using `zlibVersion`/`hdr_alloc` keeps the proof symbol distinct from the audit's red-flag names.
  - *`reinterpret_cast` of the function pointer*: rejected: the prior gates avoid it by holding a typed `constinit` function-pointer reference, and both new gates match that (no cast, no P2 exception).

### R-006: Static absorption = merge both `libhdr_histogram_static.a` and `libz.a` into `libspeedgun-ng.a`; generalize the merge module

- **Decision**: A post-build archiver step merges both vendored archives into the speedgun-ng static archive through the `ar -M` `ADDLIB` pattern. The merge mechanism is generalized from `cmake/SimdjsonArchiveMerge.cmake` into `cmake/VendoredArchiveMerge.cmake`, exposing `vendored_archive_merge(<library-target> <archived-target>...)`; 004's `simdjson_archive_merge(target)` becomes a thin named wrapper over it. This feature calls `vendored_archive_merge(speedgun-ng_speedgun-ng hdr_histogram_static zlibstatic)`.
- **Rationale**: FR-007 and FR-021/SC-009/SC-010. A static archive never absorbs the members of another archive at creation, so the installed `libspeedgun-ng.a` would otherwise leave both gate references unresolved for any consumer that pulls the gate object, and the merged archive is what makes it self-contained (the identical reasoning specs/004 R-009 records for simdjson). `nm` on the merged archive then lists `hdr_*` and zlib members with the gate references resolving in-archive. Shared configurations skip the merge: the `PRIVATE` link edge plus hidden/prefixed objects absorb both at link time (R-009, SC-004). Generalizing the archiver honors the constitution's "already in this codebase, reuse it" rule and X.2 (three copies of the same `ar -M` script is the slop). The `BUILD_INTERFACE` wrap on each `PRIVATE` link keeps the vendored names out of the exported target set (the `hwloc_vendor`/`simdjson` pattern at `CMakeLists.txt:88,155`).
- **Alternatives considered**:
  - *A third standalone `HdrhistogramArchiveMerge.cmake` copying the simdjson module*: rejected: it forks the same archiver logic a second time. One parameterized module serving three archives is smaller, and mirrors the shared-module shape of `ImportAutotoolsSubmodule`. The generalization touches 004's file only to route its existing function through the shared core; behavior is unchanged, so 004's green gates are not regressed (X.3).
  - *`$<TARGET_OBJECTS:...>`*: rejected: it enumerates object files, but the archive boundary and ordering are cleaner through the proven `ar -M` merge (specs/004 R-009 reasoning).
  - *Skip the merge for static builds*: rejected: it fails SC-009/SC-010 and leaves the future internal data-analysis consumer (this feature's named purpose) with unresolved references.

### R-007: Force each vendored library static under a shared speedgun-ng = scoped `BUILD_SHARED_LIBS OFF`

- **Decision**: Both brackets set `BUILD_SHARED_LIBS OFF` in their function scope. HdrHistogram_c additionally has `HDR_HISTOGRAM_BUILD_SHARED OFF`; zlib has `ZLIB_BUILD_SHARED OFF`. The enclosing speedgun-ng target's own `BUILD_SHARED_LIBS` is unaffected (function scope).
- **Rationale**: FR-007/FR-021 and SC-004/SC-010: a shared speedgun-ng resolves no `hdr_histogram` and no `libz` runtime object. HdrHistogram_c's static target is explicit (`hdr_histogram_static`), and its shared target is disabled; zlib's `zlibstatic` is the only zlib target once `ZLIB_BUILD_SHARED OFF`. Forcing static means no `libz.so`/`hdr_histogram.so` object exists to become an `ldd` entry; both archives' hidden/prefixed members are absorbed at speedgun-ng link time (R-006). This is the same construction specs/004 R-005 uses for simdjson, applied to two trees.
- **Alternatives considered**:
  - *Rely on `HDR_HISTOGRAM_INSTALL_SHARED OFF` alone*: rejected: that gates install only. With `HDR_HISTOGRAM_BUILD_SHARED ON` a `libhdr_histogram.so` is still built and could be named by the shared build. Both switches are set.
  - *Let zlib follow the parent's `BUILD_SHARED_LIBS`*: rejected: it produces a `libz.so` in the shared build, the exact SC-010 runtime-dependency leak the contract forbids.

### R-008: zlib redirection = vendored first, parent-scope `ZLIB::ZLIB` redirect, cache pre-seed before HdrHistogram_c's `find_package(ZLIB)`

- **Decision**: In `CMakeLists.txt`, the zlib bracket (`add_subdirectory(external/zlib ...)`) runs before the HdrHistogram_c bracket. Immediately after the zlib bracket, at parent scope:
  1. `add_library(ZLIB::ZLIB INTERFACE IMPORTED GLOBAL)` with `INTERFACE_LINK_LIBRARIES zlibstatic`.
  2. Pre-seed the `FindZLIB` cache inputs: `set(ZLIB_INCLUDE_DIR "${zlib_SOURCE_DIR}" CACHE PATH "" FORCE)`, `set(ZLIB_LIBRARY "${zlib_BINARY_DIR}/libz${CMAKE_STATIC_LIBRARY_SUFFIX}" CACHE FILEPATH "" FORCE)`, `set(ZLIB_FOUND TRUE CACHE BOOL "" FORCE)`.
  The HdrHistogram_c bracket then runs; its unguarded `find_package(ZLIB)` resolves to the vendored copy.
- **Rationale**: FR-020 requires the zlib search to resolve to the vendored copy with the host copy selected zero times. HdrHistogram_c calls `find_package(ZLIB)` at `CMakeLists.txt:57`, unguarded (it runs even with logging disabled) and non-`REQUIRED`, and consumes only the imported target `ZLIB::ZLIB` (`src/CMakeLists.txt:8`, linked PRIVATE). Mechanism, verified against CMake's `Modules/FindZLIB.cmake` and the zlib v1.3.2 tree:
  - FindZLIB is a module-mode find; it always runs first and is never short-circuited by an existing target. It calls `find_path(ZLIB_INCLUDE_DIR ...)` and `find_library(ZLIB_LIBRARY ...)`; both are no-ops when their cache variable is already set, so pre-seeding forces them to the vendored values and never probes the system prefix.
  - `find_package_handle_standard_args(ZLIB REQUIRED_VARS ZLIB_LIBRARY ZLIB_INCLUDE_DIR)` passes because both are set and point at real files (`${zlib_SOURCE_DIR}/zlib.h` exists and carries the version header `#define ZLIB_VERSION "1.3.2"` that FindZLIB parses; `ZLIB_VERSION` is guarded so it parses without the generated `zconf.h`).
  - FindZLIB guards its imported-target creation with `if(NOT TARGET ZLIB::ZLIB)`. Because the parent scope published a `GLOBAL` imported `ZLIB::ZLIB`, that check is true in the HdrHistogram_c scope, FindZLIB creates nothing, and the name still resolves to the redirect pointing at `zlibstatic`.
  - Ordering is load-bearing: zlib's `add_subdirectory` must precede HdrHistogram_c's so `zlibstatic` exists and the redirect is published before the `find_package` runs (FR-020 "build the vendored zlib ahead of HdrHistogram_c's configuration"). The zlib alias `ZLIB::ZLIB` that v1.3.2 creates at `CMakeLists.txt:161` is deliberately not relied on: an `ALIAS` target is directory-scoped and invisible to a sibling `add_subdirectory`, and `ZLIB_BUILD_SHARED OFF` means that alias is not even created. The parent-scope `IMPORTED GLOBAL` redirect is the sibling-visible handle.
  - The redirect carries `zlibstatic`'s usage requirements, so compiling `hdr_histogram_log.c` against `<zlib.h>` gets both the source `zlib.h` and the binary-dir generated `zconf.h` from the static target's `INTERFACE_INCLUDE_DIRECTORIES`. The pre-seeded single `ZLIB_INCLUDE_DIR` is only what FindZLIB inspects for its own version parse; the actual compile reaches the generated header through the target.
- **Alternatives considered**:
  - *Rely on zlib's own `ZLIB::ZLIB` alias satisfying the search*: rejected: aliases are directory-scoped (invisible to siblings) and require `ZLIB_BUILD_SHARED ON` (a runtime-dependency leak). Verified: the alias alone also does not satisfy `find_package`, because FindZLIB still requires `ZLIB_LIBRARY`/`ZLIB_INCLUDE_DIR` and re-runs regardless of an existing alias.
  - *`-DZLIB_ROOT=<vendored>` alone*: rejected: FindZLIB would then search the vendored tree for a `libz` artifact and `zlib.h`+`zconf.h` in the layout it expects; the generated `zconf.h` lives in the build tree. That layout is unlike an install prefix, so the search either fails or risks a system fallback on a machine that carries zlib. The cache pre-seed plus the explicit redirect target is deterministic.
  - *Point `ZLIB_INCLUDE_DIR` at a scratch dir containing both `zlib.h` and `zconf.h`*: rejected: creating a synthesized include directory duplicates headers and adds a step. The redirect target already supplies both include dirs to the compile; FindZLIB needs only `zlib.h` for its version parse.

### R-009: Symbol privacy = HdrHistogram_c compiled hidden; zlib compiled hidden plus `Z_PREFIX` renaming

- **Decision**: Both brackets set `CMAKE_C_VISIBILITY_PRESET hidden` (and `CMAKE_CXX_VISIBILITY_PRESET hidden`) so every vendored object is stamped `STV_HIDDEN`. zlib additionally compiles with `Z_PREFIX ON`, so its public symbols rename (`inflate` → `z_inflate`, `deflate` → `z_deflate`, `compress` → `z_compress`, `uncompress` → `z_uncompress`, ...) via the `zconf.h` rename macros. The speedgun-ng static absorption (R-006) keeps both archives inside `libspeedgun-ng.a`.
- **Rationale**: FR-017 and FR-022 with SC-004/SC-011. HdrHistogram_c sets no visibility property and carries no symbol-prefix mechanism (verified: no `CXX/C_VISIBILITY_PRESET`, no `-fvisibility`, no prefix macro anywhere in its CMakeLists); its public C symbols are the `hdr_` family. `CMAKE_C_VISIBILITY_PRESET hidden` in the bracket stamps every `hdr_` symbol hidden, so a shared speedgun-ng exports zero of them and zero names match the `hdr_` prefix (SC-004). zlib's `HAVE_HIDDEN` compile definition hides only `ZLIB_INTERNAL` helpers, never the public `ZEXTERN` API (`inflate`/`deflate`/`compress`/`uncompress` stay default-visible under `HAVE_HIDDEN` alone), so hidden visibility must land on the compile via the bracket's `CMAKE_C_VISIBILITY_PRESET`, and FR-022 additionally names `Z_PREFIX` as the renaming control equivalent to hwloc's `sg_` prefix. `Z_PREFIX` is the deterministic control for a dependency's public surface the constitution prefers (a documented dependency knob, applied through the generated `zconf.h`, so every consumer of the vendored target compiles consistently against the renamed prototypes). The bare names `inflate`/`deflate`/`compress`/`uncompress` therefore never exist in the build, and hidden visibility removes the renamed symbols from a shared build's dynamic table (SC-011).
- **Alternatives considered**:
  - *`-Wl,--exclude-libs,ALL` at the shared link*: rejected: the objects are compiled hidden in-tree, so the leak is closed at its source; a repo-wide linker flag touches every target's gate surface to solve a case already handled at compile time (specs/004 R-007 reasoning).
  - *`HAVE_HIDDEN` alone for zlib*: rejected: it hides only internal helpers, leaving `inflate`/`deflate`/`compress`/`uncompress` exported (SC-011 violation). `Z_PREFIX` plus compile-time hidden visibility is required.
  - *Rename HdrHistogram_c too*: rejected: no upstream prefix mechanism exists, and its `hdr_` prefix is already distinct enough; hidden visibility plus static absorption removes collision and export (the spec assumption states collision avoidance for HdrHistogram_c rests on hidden visibility plus absorption).

### R-010: Install-rule suppression = zlib via `ZLIB_INSTALL OFF`; HdrHistogram_c via a scope-limited `install()` override

- **Decision**:
  - zlib: `ZLIB_INSTALL OFF` removes every zlib install rule; no further neutralization is needed.
  - HdrHistogram_c: the two options kill the gated installs (library-target, `install(EXPORT)`), and `HDR_HISTOGRAM_BUILD_PROGRAMS OFF` kills the test/example installs, but three rules run unconditionally: `install(FILES hdr_histogram-config.cmake ...)` (`CMakeLists.txt:97`), `install(FILES hdr_histogram.pc ...)` (`CMakeLists.txt:121`), and `install(FILES ${HDR_HISTOGRAM_PUBLIC_HEADERS} DESTINATION include/hdr)` (`include/CMakeLists.txt:12`). The ingestion neutralizes these three with an `install()` command override scoped to the ingestion function (the definition site of the HdrHistogram_c bracket), so `EXCLUDE_FROM_ALL` plus the override leave nothing in `CMAKE_INSTALL_PREFIX`.
  - Both: the speedgun-ng install rules already live in the separate `cmake/install-rules.cmake`, so a scope-limited override at the bracket site does not neutralize speedgun-ng's own installs.
- **Rationale**: FR-012. `EXCLUDE_FROM_ALL` excludes a target from the default build but does not stop an `install()` call in the subdirectory from registering a rule in that subtree's generated `cmake_install.cmake`, which the parent install runs. The three unconditional rules have no option to turn off. The `install()` override (a function/macro named `install` defined in the bracket's scope, shadowing the built-in for the `add_subdirectory` subtree) is the concrete mechanism the spec assumption requires the plan to record. Its scope discipline: the override is defined only inside the ingestion function, and the speedgun-ng export/install happens in `cmake/install-rules.cmake` included elsewhere, so speedgun-ng's install behavior is unchanged (this is the mechanism to verify empirically at implement per the quickstart). zlib needs none of this because its v1.3.2 install block is wholly under `if(ZLIB_INSTALL)`.
- **Alternatives considered**:
  - *Point `CMAKE_INSTALL_INCLUDEDIR`/`LIBDIR` at a scratch path for the HdrHistogram_c subtree*: considered as the fallback if the override misbehaves on a generator; rejected as the primary because a scratch tree holds stray files and weakens the SC-002 audit's zero-install clarity.
  - *Accept the three installs*: rejected: FR-012 requires zero vendored files in `CMAKE_INSTALL_PREFIX`, and a leaked `hdr_histogram-config.cmake`/`.pc`/`hdr/*.h` is exactly the leak FR-019/SC-002 audits for.
  - *Fork a patched HdrHistogram_c CMakeLists*: rejected: the pinned submodule is the source of truth (FR-001); patching it breaks SC-007 (pristine worktree) and the re-pin story (FR-006).

### R-011: The exemptions hwloc gets for free must be built explicitly = scoped variable-reset brackets around each `add_subdirectory`

- **Decision**: One helper function per vendored tree wraps its `add_subdirectory` call. Inside each, before the call, the same set specs/004 R-006 established is reset in function scope: `CMAKE_C_FLAGS ""` and `CMAKE_CXX_FLAGS ""` (drop parent strict warnings, `-Werror`, hardening), `CMAKE_C_FLAGS_SANITIZE`/`CMAKE_CXX_FLAGS_SANITIZE ""` and `CMAKE_C_FLAGS_COVERAGE`/`CMAKE_CXX_FLAGS_COVERAGE ""` (no sanitizer, no `--coverage`), `CMAKE_C_CLANG_TIDY`/`CMAKE_CXX_CLANG_TIDY ""` and `CMAKE_C_CPPCHECK`/`CMAKE_CXX_CPPCHECK ""` (no static analysis of vendored code), `CMAKE_C_VISIBILITY_PRESET hidden` and `CMAKE_CXX_VISIBILITY_PRESET hidden` (R-009), `CMAKE_POSITION_INDEPENDENT_CODE ON` (R-006), `BUILD_SHARED_LIBS OFF` (R-007), plus each tree's option constants (R-004). Targets created inside a function persist to the caller's build system, so the `hdr_histogram_static` and `zlibstatic` handles are usable at the call site.
- **Rationale**: FR-009 and FR-010. This is the CMake-child inheritance asymmetry specs/004 R-006 records: a CMake `add_subdirectory` child inherits the parent's `CMAKE_C_FLAGS`, `CMAKE_C_FLAGS_<CONFIG>`, `CMAKE_C_CLANG_TIDY`, `CMAKE_C_CPPCHECK` (the vendored trees are C). Both vendored projects are C (`LANGUAGES C`), so the `C_` family variables carry the inherited gates and must be blanked alongside the `CXX_` family that 004 blanked for the C++ simdjson. Without the bracket: the sanitizer preset (`CMAKE_CXX_FLAGS_SANITIZE`, `CMakePresets.json:130`) instruments the vendored archives (FR-010), the coverage preset injects `--coverage`, the strict `-Werror` set (`CMakePresets.json:61`) fails the vendored C sources, and tidy/cppcheck analyze vendored code (FR-009). Function scope realizes the spec-mandated exemptions that are structural for the hwloc autotools child. The coverage extraction whitelist (`cmake/coverage.cmake`) already keeps `external/` out of the report; blanking the coverage flags additionally stops instrumentation from being emitted. Mixing sanitizer-instrumented callers with an uninstrumented static dependency is supported by ASan/UBSan (specs/003 R-008, 004 R-006 rationale).
- **Alternatives considered**:
  - *Per-target property clearing after `add_subdirectory`*: rejected for the config flags: they come from `CMAKE_C_FLAGS_<CONFIG>` applied at generation from the directory scope; a post-hoc property edit cannot subtract them. The scope reset is the only point they can be neutralized before the child targets generate.
  - *Editing the presets to omit `external/`*: rejected: presets are shared by every target; narrowing them weakens the gates for all code (constitution VIII).

### R-012: Wrapper include under the strict gate set = vendored headers as SYSTEM for both gate TUs

- **Decision**: After each `add_subdirectory`, promote the vendored target's interface include directory into its `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES`. `source/hdrhistogram/hdrhistogram_gate.cpp` then compiles `<hdr/hdr_histogram.h>` via `-isystem`; `source/zlib/zlib_gate.cpp` compiles `<zlib.h>` (and transitively the generated `<zconf.h>`) via `-isystem`. The gate files' own lines stay under the strict `-Werror` set.
- **Rationale**: FR-009 and FR-014 with the specs/004 R-008 mechanism. The gate TUs belong to the speedgun-ng target, which carries the strict warning set with `-Werror`; vendored headers are not written to that baseline. `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES` has existed since CMake 2.8 and keeps the plan at the 3.20 floor (the `add_subdirectory(... SYSTEM ...)` keyword needs 3.25, rejected as in 004). Because the vendored include interface reaches the generated `zconf.h` through the target's include dirs (R-008), the SYSTEM promotion covers it too.
- **Alternatives considered**:
  - *`add_subdirectory(... SYSTEM ...)`*: rejected: needs CMake 3.25, above the project floor (specs/004 R-008).
  - *Compile the gate TU with `-w`*: rejected: it silences the gate's own lines, contradicting FR-009's "speedgun-ng code that calls the vendored library is held"; the SYSTEM include suppresses only header-originated diagnostics.

### R-013: Audit and gate wiring = extend the existing scripts, CI jobs, and classifier; two audit patterns

- **Decision**:
  1. Two audit patterns per FR-019: the HdrHistogram_c pattern is the case-insensitive regex `hdr[-_]?histogram` (covers `hdr_histogram`, `hdr-histogram`, `hdrhistogram`); the zlib pattern is the case-insensitive pair `zlib`/`libz`. The shared-build symbol audit additionally flags any exported symbol starting with `hdr_`, and its zlib half additionally names `inflate`/`deflate`/`compress`/`uncompress` (SC-004, SC-011).
  2. `tools/hdrhistogram/hdrhistogram_purity_scan.sh` and `hdrhistogram_nm_proof.sh`, and `tools/zlib/zlib_purity_scan.sh` and `zlib_nm_proof.sh`, modeled on the `tools/simdjson` pair and registered in `test/CMakeLists.txt`. The HdrHistogram_c purity scan greps discovery-call form of the FR-019 pattern over project build files (excluding `external/`) and the pattern under `include/`. A `find_package(ZLIB)` call in the project build files is permitted: the search is redirected while the host resolution stays forbidden. The zlib purity scan asserts no `find_package`/`pkg_check_modules` naming zlib under any `zlib`/`libz` spelling resolves to the host; the host-resolution proof is the SC-010 configure-record check in CI, and the purity scan leaves it to that check.
  3. `tools/dbc/dependency_scan.sh` gains classifier branches so the `hdr_histogram*` and `zlib*`/`ZLIB::ZLIB` `PRIVATE` links classify as vendored-private (the existing `hwloc_vendor`/`simdjson` branch shape, lines 96-103), keeping `dbc_dependency_scan` green.
  4. `.github/workflows/ci.yml`: every checkout already carries `submodules: true`, so both new submodules are fetched unchanged. The `test` job gains install-tree and package-config audits for both (patterns `hdr[-_]?histogram` and `zlib`/`libz`). `shared-audit` gains `nm -D`/`ldd` steps for both plus the `hdr_`-prefix export check. `downstream-consumer` installs a system `libhdrhistogram-c-dev` and `zlib1g-dev` and greps the consumer logs for both patterns. No new host toolchain: both trees are CMake-native.
  5. `CMakePresets.json`: no change. Its `clang-tidy` preset already carries `--exclude-header-filter=^${sourceDir}/external/` (line 43), covering both new submodules. `.codespellrc` already skips `*/external` (line 8), and `cmake/lint.cmake`'s PATTERNS whitelist never matches `external/`, so neither tree enters lint or spell.
- **Rationale**: FR-008, FR-009, FR-015 through FR-022. The infrastructure specs/003 and 004 built (submodule checkouts, shared-audit, downstream-consumer, purity/nm script pair, the dependency classifier) is exactly the surface this feature extends; reuse keeps each failure diagnosis readable. The repo-spelling-only audit is insufficient: upstream names HdrHistogram_c artifacts `hdr_histogram`, so a `hdrhistogram`-only search would pass vacuously over a real leak (FR-019). `zlib1g-dev` is nearly always present on the runner, which strengthens SC-010: the build must prove it selects the vendored zlib over an ever-present host copy.
- **Alternatives considered**:
  - *One combined audit script for both trees*: rejected: the two patterns differ (`hdr[-_]?histogram` versus `zlib`/`libz`) and the HdrHistogram_c audit carries an extra `hdr_`-prefix export check while the zlib audit carries the `inflate`/`deflate` absence check; separate scripts keep each verdict readable.
  - *Add `external/hdrhistogram_c`/`external/zlib` to `.codespellrc`/tidy filter explicitly*: rejected as redundant: the `*/external` skip and the `^${sourceDir}/external/` header exclude already cover both.
  - *Skip the `dependency_scan` classifier edit*: rejected: the scan flags a `target_link_libraries(... hdr_histogram_static ...)` line as `library-runtime`; the vendored-private classification is the documented path the existing hwloc/simdjson entries use.
